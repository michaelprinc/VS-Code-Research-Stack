Notebook pair: the refusal and the reviewed fallback, measured — 3 November 2026, this host
============================================================================================

What this proves: the notebook analysis project the toolkit writes into the workspace behaves the same
way as the worker project when a host's uv disagrees with the lock — it is refused by `--locked` on every
uv version tested, and the one reviewed `--frozen` fallback installs what the lock pins without rewriting
the lock. This is the pair the notebook step points at, so it is the pair the fallback could be used on.

Refusal exit codes follow the same split measured for the worker pair in uv-matrix.txt: 2 on 0.5.0 to
0.7.22, 1 from 0.8.5 on. `--frozen` exits 0 on both ends of the supported range and never rewrites the
lock, which is why the toolkit's rule that setup never runs `uv lock` in a managed directory still holds
inside the fallback.

How the step uses this
----------------------
extension/steps.js runNotebookStep: one `uv sync --locked --no-dev --python 3.12 --project <project>
--no-config`; if uv refuses with the staleness sentence, the toolkit re-reads the pair with its own
reader (notebookPairProblems). If the reader agrees the pair disagrees, it refuses and names both files
— no fallback. If the reader says the pair is current, it runs exactly one `--frozen` attempt and records
the fallback. The reader's own verdict on a pair with a drifted root version is "root package version
does not match pyproject version", so a drifted pair is refused, not installed through the fallback.
