# 06 · Windows semantics checklist, mapped to this toolkit

Each row is a Windows behaviour that breaks Linux-developed software. Status is against the code as shipped
in 0.3.8 (`v0.3.8` = `7638898`). "Needs Windows proof" means the code looks right and has a shape test, but
has never executed on Windows.

## A. Encoding

| Windows behaviour | Why it bites | Status here |
|---|---|---|
| CPython uses UTF-8 for the **console device** but the **ANSI code page (`mbcs`) for pipes and redirected files** ([sys docs](https://docs.python.org/3/library/sys.html), [PEP 540 annex](https://peps.python.org/pep-0540/)) | `execFile` captures stdout as a **pipe**, so a Python child on Windows encodes with cp1252 and Node decodes it as UTF-8 | **This was the 0.3.7/0.3.8 defect.** Fixed by `PYTHON_FLAGS = ["-I","-B","-X","utf8"]` in [runner.js:63](../../../extension/runner.js#L63) + `ensure_ascii=True` in the CLI + a U+FFFD refusal in `steps.js`. Needs Windows proof. |
| `-I` (isolated) implies `-E` and `-s`, so **`PYTHONUTF8` and `PYTHONIOENCODING` are silently dropped** ([cmdline docs](https://docs.python.org/3/using/cmdline.html#option-I)) | An env-var-only fix would not have worked under the toolkit's own `-I` | **Correctly handled**: the fix is the `-X utf8` flag, not an env var. Worth a comment in the code so nobody "simplifies" it to `PYTHONUTF8` later. |
| `PYTHONIOENCODING` is ignored for interactive Windows console buffers unless `PYTHONLEGACYWINDOWSSTDIO` is set | A fix that works when piped can fail when attached, and vice versa | Not applicable (always piped), but record it. |
| stderr's error handler is **always** `backslashreplace` on Windows | Non-ASCII in a traceback arrives as `\u010d` escapes, so a log-scraping regex that expects raw characters silently misses | **Gap.** `runner.js`'s `CODEC_SIGNATURE` / `isCodecFailure` matching should be tested against an escaped form, not only the raw one. |
| `chcp` changes the code page only for **programs started after it**; already-running processes keep the old one ([chcp](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/chcp)) | A "run `chcp 65001` first" instruction fixes the child but not the extension host | Already acknowledged in `installer.js:443` (tell the user to use a UTF-8 terminal, `chcp 65001` in cmd.exe). Good. |
| PowerShell 5.1 writes UTF-16LE via `>` and defaults `$OutputEncoding` to ASCII; PS 7 defaults to `utf8NoBOM` ([about_Character_Encoding](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding)) | Any future `powershell.exe` call returns BOM'd UTF-16 or ANSI-mangled text | Not currently used by the toolkit. Keep it that way, or decode explicitly. |
| `ensure_ascii=True` output is encoding-agnostic | ASCII survives cp1252, cp850, UTF-8 and `backslashreplace` alike | **Handled** in 0.3.8. Keep it as a rule for anything crossing the process boundary. |

## B. Paths

| Windows behaviour | Why it bites | Status here |
|---|---|---|
| `MAX_PATH` = 260; long-path support needs **both** `LongPathsEnabled=1` **and** a `longPathAware` manifest, and the registry value is cached per process ([Maximum Path Length Limitation](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation)) | A deep `.research-toolkit/managed/worker-<ver>/…` tree fails on a machine where the key is off | **Measured, not guessed**: `probes/path_budget.py` walks 7 Windows roots × 8 toolkit-relative paths over the real field root; worst case fits with **83 characters of headroom**. That headroom is small and it is *not* a proof — it depends on the user's folder name. Needs Windows proof. |
| A spawned child's `cwd` is subject to `CreateProcess` limits even where Node's `fs` survives a long path via the namespace prefix (`path.toNamespacedPath`, [docs](https://nodejs.org/api/path.html)) | `fs.mkdir` succeeds, then `python.exe` with that `cwd` fails | **Gap.** Worth a probe that compares `fs` access and a spawned child's `cwd` acceptance at the same depth. |
| `git core.longpaths` is **disabled by default** in Git for Windows ([core.adoc](https://github.com/git-for-windows/git/blob/main/Documentation/config/core.adoc)) | `git clone`/`checkout` of the toolkit repo itself fails on Windows with "Filename too long" | **Gap.** `.gitattributes` is `* text=auto eol=lf` (good), but no long-path guidance in the docs. |
| Reserved names `CON PRN AUX NUL COM1-9 LPT1-9`, **including with an extension** (`NUL.txt`) and with superscript digits (`COM¹`) ([Naming a File](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)) | A generated step/guide/worker name that happens to be `aux` or `con.json` is uncreatable | **Gap.** Linux happily creates `CON`, `nul`, `COM1`, `aux` — measured here. Add a static guard over every generated name (ids, folder names, artifact names). Oracle: `PureWindowsPath("CON.txt").is_reserved()` → `True` (Python 3.12; `os.path.isreserved()` from 3.14; `PurePath.is_reserved()` removed in 3.15). |
| Illegal characters `< > : " / \ \| ? *`, control chars 1–31; **names must not end with a space or a period** | A Linux-created `a:b.json` or `dir.` cannot be written, extracted, or enumerated on Windows | **Gap** for generated names. The field root itself contains none of these, but it contains spaces and diacritics. |
| Case-insensitive, case-preserving lookups; NTFS case sensitivity is **not** the default | Two artifacts differing only in case collapse into one file | **Verified on the real mount** (`RESEARCH.SQLITE3` and `research.Sqlite3` are the same 77,824-byte file). **Gap:** no static collision guard over the toolkit's own generated names. `ntpath.normcase` is the right oracle; Node 24 has **no** `path.win32.normcase`. |
| Alternate data streams / Mark-of-the-Web (`Zone.Identifier`) | A downloaded VSIX or a written `.ps1`/`.bat` is blocked or warned; directory-walking code treats `file:Zone.Identifier` as a file | **Cannot be emulated here** — `os.listxattr()` on the 9p mount returns `[]`. Needs a real Windows host. |
| Drive letters, mapped drives, UNC, per-drive current directory | `path.relative()` and `startsWith(workspaceRoot)` break when the workspace is on `Z:` or `\\server\share` while the tool is on `C:` ([vscode-python#24525](https://github.com/microsoft/vscode-python/issues/24525)) | **Partly handled**: `hosttools.js` has `joinPath(platform, …)` and platform-driven known locations. **Gap:** no test with a workspace on a *different* drive than the extension host. |
| Symlinks need `SeCreateSymbolicLinkPrivilege` or Developer Mode ([Create symbolic links](https://learn.microsoft.com/en-us/windows/security/threat-protection/security-policy-settings/create-symbolic-links)) | A fixture that `fs.symlink`s a fixture fails with `EPERM` only on Windows | **Gap** if any test or install step symlinks. Junctions are the Windows-native alternative. |
| `%USERPROFILE%`/`%APPDATA%`/`%LOCALAPPDATA%`, no `HOME` | `process.env.HOME` is `undefined` on Windows | **Handled**: `hosttools.js:42-47` reads `USERPROFILE`, `LOCALAPPDATA`, `APPDATA`. |

## C. Process creation and control

| Windows behaviour | Why it bites | Status here |
|---|---|---|
| `.bat`/`.cmd` **cannot** be launched with `execFile` at all ([child_process docs](https://nodejs.org/api/child_process.html)) | `spawn('npm', …)` → `ENOENT` on Windows | **Handled**: `hosttools.js:24,149` refuses `WINDOWS_WRAPPER_EXTENSIONS` under `shell:false`, and `runner.js:491` recognises `uv(.exe\|.cmd\|.bat\|.com)`. |
| `shell: true` with an args array is a **runtime deprecation** (DEP0190, Node 24): args are space-joined, not escaped | Command injection through a workspace path | **Handled**: `shell: false` at every call site. Keep it as an enforced invariant (see the ESLint proposal in `methodology.md`). |
| `cmd.exe` is a text preprocessor: `( ) % ! ^ " < > & \|` trigger transformations; `child "x\" &whoami` runs `whoami` ([Everyone quotes command line arguments the wrong way](https://learn.microsoft.com/en-us/archive/blogs/twistylittlepassagesallalike/everyone-quotes-command-line-arguments-the-wrong-way)) | A workspace path containing `&` splits the command | **Handled in the pasteable instruction path**: `installer.js:404` quotes with the `CommandLineToArgvW` rules and names `K:\A&B` as the example. Needs Windows proof. |
| MSVC argv parsing: a **trailing backslash before a quote** merges arguments | `"C:\dir\"` + `"arg"` becomes one token | Covered by the same quoting helper; add a fixture with a path ending in `\`. |
| `windowsHide` defaults to **false** | A console window flashes for every `git`/`rg`/`python` call ([vscode#137481](https://github.com/microsoft/vscode/issues/137481)) | **Handled**: `windowsHide: true` at the reviewed boundary. Needs Windows proof. |
| No POSIX process groups; `os.killpg` is Unix-only; `Popen.kill()` == `TerminateProcess()`; `kill('SIGTERM')` hard-kills with no flush ([os docs](https://docs.python.org/3/library/os.html)) | Orphaned `uv` grandchildren survive ([vscode#320573](https://github.com/microsoft/vscode/issues/320573)) | **Handled in shape**: `reapTree()` uses `taskkill /PID <pid> /T /F` on win32 and `process.kill(-pid, "SIGKILL")` on POSIX, with a bounded, never-rejecting reaper. **Never executed on Windows** — the single highest-value Windows proof to obtain. |
| `detached` is **silently dropped** by `execFile` (it forwards only `cwd, env, gid, shell, signal, uid, windowsHide, windowsVerbatimArguments`) | A "background" child still blocks parent exit | **Handled and documented** in `runner.js:30`; `detached: os.platform() !== "win32"` at `runner.js:139`. |
| `process.kill(pid, 0)` tests existence, but "Windows platforms will throw an error if the pid is used to kill a process group" ([process docs](https://nodejs.org/api/process.html)) | A liveness probe written for POSIX breaks on Windows | `preflight.js:46` uses `process.kill(pid, 0)` with an `ESRCH` check — single pid only, so it is fine. Add a Windows test so this stays true. |
| Exit codes on Windows are raw 32-bit Windows codes (`0xc0000142` = `STATUS_DLL_INIT_FAILED`), and negative "killed by signal N" is POSIX-only ([vscode#344012](https://github.com/microsoft/vscode/issues/344012)) | `code & 0xFF` or `code < 0` logic misreads a Windows failure | **Gap.** Check how `runner.js`'s `classify()` treats large unsigned codes and `null` `signalCode`. |
| Antivirus/Defender scans and can block or delete freshly extracted executables ([process exclusions](https://learn.microsoft.com/en-us/microsoft-365/security/defender-endpoint/configure-process-opened-file-exclusions-microsoft-defender-antivirus)) | `spawn` fails with EACCES/EPERM on a user's machine, not on yours | **Unknowable from Linux.** Treat as a field-host gate item; document it in the troubleshooting notes. |

## D. Environment

| Windows behaviour | Why it bites | Status here |
|---|---|---|
| Environment variable **names** are case-insensitive on Windows; when spawning, Node "lexicographically sorts the `env` keys and uses the first one that case-insensitively matches" ([child_process docs](https://nodejs.org/api/child_process.html)) | A `PATH` prepend is ignored, or the wrong one of `Path`/`PATH` wins | **Partly handled**: `hosttools.js:90` lowercases PATH entries for win32 scanning. **Gap:** `hosttools.js:193` and the spawn path read `env.PATH` from an object that may be a plain object in tests. Add a fixture whose env uses Windows' real mixed-case names (`Path`, `Temp`, `LocalAppData`, `ComSpec`, `PATHEXT`). |
| VS Code-spawned processes can be missing `PATHEXT`, `ComSpec`, `APPDATA`, `LOCALAPPDATA`, `ProgramFiles` ([vscode#344072](https://github.com/microsoft/vscode/issues/344072), [vscode#332707](https://github.com/microsoft/vscode/issues/332707), both open) | Tool discovery returns nothing on a real Windows machine | **Gap, and the most likely next Windows defect.** `hosttools.js` already guards `env.USERPROFILE && …` — keep that style, and add a discovery test with a stripped env. |
| `HOME` does not exist; `os.userInfo()` returns `uid/gid = -1`, `shell = null` on Windows | `path.join(undefined, …)` | Handled via `USERPROFILE`. |
| `os.EOL` is `\r\n`; PowerShell pipes native commands with CRLF | A `\n`-splitting parser leaves `\r` in every value | **Gap** for any line protocol (the setup log is JSON-lines). Check the reader against CRLF input. |

## E. VS Code-specific

| Behaviour | Why it bites | Status here |
|---|---|---|
| `extensionKind` decides whether `process.platform` is Windows at all: in a remote/WSL host a "workspace" extension runs on the remote OS | The same code sees `linux` on a Windows user's desktop | **Gap.** Nothing in `setuplog.js`/`preflight.js`/`status.js` records `process.platform` or `process.arch`. Recording them costs one field per log line and makes every future field report classifiable. |
| Extensions live in `%USERPROFILE%\.vscode\extensions\<publisher>.<name>-<version>` | Already deep; a nested cache crosses 260 chars ([vscode#300594](https://github.com/microsoft/vscode/issues/300594)) | The toolkit's state lives in the **workspace** (`.research-toolkit/`), which is better for this project, but the extension folder depth still counts toward the managed-runtime path if it is ever placed under the extension dir. |
| Windows arm64 exists (`win32-arm64`, `windows-11-arm` runners) | A `win32-x64`-only assumption | **Gap** only if native binaries are ever shipped. The toolkit is pure JS + Python, so a single VSIX is correct — but `process.arch` should still be logged. |
| Publishing from Windows strips POSIX exec bits from packaged files ([Publishing extensions](https://code.visualstudio.com/api/working-with-extensions/publishing-extension)) | A Windows-built VSIX breaks `node_modules` binaries on Linux | Keep packaging on Linux. |
