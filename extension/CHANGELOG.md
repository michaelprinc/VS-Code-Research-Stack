## 0.3.14 — 17 November 2026 · the store retrieves with two rankers, the presets reach the store, and a bundle you edited is not lost

Every figure below is measured from this tree — `extension/presets.json`, `src/research_stack/vectors.py`, `src/research_stack/records.py`, `src/research_stack/presets.py`, `src/research_stack/lab_server.py`, `extension/bundles.js`, `extension/package.json`, `extension/integrationprobe.js` — and from the vendor name-list arithmetic recorded in `research/github-mcp-tool-map-2026-11-17.md`. The release gates have **not** been run for 0.3.14 here: `extension/package.json` and `extension/vsix-manifest.json` now carry the `0.3.14` stamp, but no `research-stack-toolkit-0.3.14.vsix` exists in `dist/`, so `check:payload` and `verify-package` have nothing 0.3.14 to audit and the newest built artifact in this repository remains `research-stack-toolkit-0.3.13.vsix`. Package-level test results are named below with that limit stated.

**Retrieval got a second ranker, and it is told apart from the first.** `search_corpus` answers in three modes — `lexical` (the stored BM25 path, unchanged in ranking, in hit fields and in the verb envelope: `vector` and `hybrid` are what moved, and a lexical hit carries no new key), `vector`, and `hybrid`. The vectors come from the Toolkit's own CPU backend, `rsk-hashing-v1`, **256** dimensions, word tokens plus character 3- and 4-grams combined by signed feature hashing, weights `1 + ln(count)`, summed in sorted feature order, L2-normalised, quantised to signed 16-bit and stored as base64 (`base64-int16-le`). Standard library only: no model download, no network call, no new dependency in `pyproject.toml` or `uv.lock`, no third-party database. It is a **lexical signature**, not a semantic model — `iluminace` reaches `iluminacích`, and "pilgrimage" and "journey" are not the same idea to it. Unrelated English text measured ≈ 0.21 cosine, so **no cosine threshold is applied anywhere**: the modes rank, they do not decide relevance. `hybrid` fuses the two rankings by a published rule reported in the receipt — `0.5 × reciprocal-rank-fusion (k = 60, normalised so a chunk first in both rankers scores 1.0) + 0.25 × best-normalised BM25 + 0.25 × best-normalised cosine`, weights summing to 1.0, candidate pool `min(50, max(limit × 3, 20))`, ties broken on source path, then locator, then chunk id — and every vector or hybrid hit carries `retrieval` with `lexicalRank`, `lexicalScore`, `vectorRank`, `vectorScore`, `fusedScore` and `backend`, so the reader can see which ranker placed the passage. A stored vector is used only when its `backend_id`, its `dimensions` **and** the hash of the chunk text it was made from all match what this backend would compute today; a row that fails is counted as stale, never scored, and the refusal says why (`SEARCH_MODE`, `VECTORS_MISSING`, `VECTOR_BACKEND_STALE`, each naming the verb to run). `embed_corpus` is the new verb that builds them, from the chunk text the store already holds — no source file is opened, which is what makes a re-index possible for a store whose sources are gone.

**Schema 4, and a migration that invents nothing.** `SCHEMA_VERSION` is **4** (`SUPPORTED_SCHEMA_VERSIONS (1, 2, 3, 4)`). The 3 → 4 migration adds one table, `chunk_vectors` (chunk id, backend id, dimensions, the hash of the chunk text the vector came from, the vector, the timestamp), and nothing else: no source, chunk, claim or evidence row is rewritten, and **no vector is computed during a migration** — that is verb work. A store migrated from 0.3.13 keeps every chunk identity and every claim link it had, opens with lexical search working, and refuses `vector` and `hybrid` with `VECTORS_MISSING` naming `embed_corpus`. The 0.3.13 lexical ranking is proven unchanged by running the pristine 0.3.13 tree in a subprocess and comparing its hits against the migrated store's, not by restating them.

**`lab-state.json` is derived, not promised.** Every store-writing verb rewrites the file from a query against the database — `refreshedAt`, `refreshedBy`, the counters, `storeSchemaVersion`, and a `vectorSearch` block that states the retrieval state as `not-built`, `partial`, `stale` or `ready` with `vectorCount`, `currentChunkCount`, `scoreableChunks` and `staleVectorCount`, plus the verb to run. The file says what it is ("Derived record… if the two disagree the store is the record"), and `store_status` answers from the same query. Where a store must be migrated before this build may read it — a backup or an activated restore on an older schema — the receipt names the schema code and the step to run instead of writing counters it did not measure. The 0.3.13 report was right that its numbers matched only by accident. `draft` is now a claim status (`open`, `draft`, `supported`, `contested`, `rejected`, `closed`): a statement not assessed yet, and an unknown status is still refused.

**Twelve preset ids, three of them max, and each one names its tools.** `extension/presets.json` declares **12** preset ids — ten offered by a package, two retired. `budget.toolkitCeilingPerPreset` is **20** (0.3.13 shipped 12); `clientCeiling` stays 128 and `minimumHeadroom` stays 20. The workers register **21** verbs across the three managed servers (5 document, 5 metadata/Zotero, 11 store — `embed_corpus` is the new one), and the rule changed with the cap: a third-party entry names the exact tools it selects and its count **is** the length of that list; an unnamed vendor estimate is no longer an acceptable shape.

- **`research-max-github-full`** — **16** toolkit verbs + **92** named GitHub tools (every name in the vendor's published local catalog, `GITHUB_TOOLSETS=all` or the remote `/x/all`) = **108** of 128, leaving exactly the **20** tools of headroom the budget keeps. It names the five verbs it leaves out and why: `search_local_text` (the stored index is this preset's search surface), `zotero_write` and `prepare_zotero_import` (a repository-centred goal does not write a reference library), `unindex_corpus` and `store_maintenance` (the destructive pair lives in `corpus-lab` and `research-max-no-github`).
- **`research-max-github-limited`** — **20** toolkit verbs + **42** named read-only GitHub tools = 62, 66 tools of headroom. The selection carries the server's own read-only switch (`GITHUB_READ_ONLY` / `X-MCP-Readonly`, `/mcp/readonly`) **and** an `excludeTools` list naming all **35** write tools in the catalog. Read-only in the tool surface is not a permission boundary: what the account may do is decided by the token, not by this preset.
- **`research-max-no-github`** — **20** toolkit verbs and no third-party surface, 108 tools of headroom. The verb it leaves out is `search_local_text`; the Toolkit writes no GitHub entry for it, and the preset names the operator steps that take Copilot's built-in GitHub server out of the surface (no `github` entry in the MCP configuration, and the GitHub group unchecked in **Chat: Open Customizations → Tools**).
- `research-workflow`, the Full default, goes **11 → 15** verbs — `embed_corpus`, `verify_sources`, `claims_export` and `store_status` join, so the journey reaches the export and the freshness check instead of ending at `claims_write`. `corpus-lab` goes **11 → 12** with `embed_corpus`. `read-and-cite`, `find-in-notes`, `verify-citations`, `zotero-handoff` and `research-core` are unchanged.
- **`research-lab` and `research-lab-max` are retired, not deleted.** They carry `retired: true` and a named `successor`, no package offers them, and their ids stay registered in the worker so a saved 0.3.13 preference resolves to a stated retirement instead of falling back in silence. They are retired because their whole third-party content was an unnamed estimate — 52 GitHub + 24 Playwright + 15 Zotero tools for servers this Toolkit never inventoried — and because `research-lab-max` was the preset carrying **no lab verb at all**, which is the defect this release started from.

**GitHub figures in these presets are vendor catalog names, not measurements.** No GitHub MCP server was started on this host and no `tools/list` was captured, so 92, 42 and 35 are name counts derived from the vendor's published catalog and its `ReadOnlyHint` values, as recorded in `research/github-mcp-tool-map-2026-11-17.md`. A `tools/list` on a real host is still owed, and 24 published tool-name aliases mean an allow-list must use canonical names.

**New command: Configure Preset Tools for Copilot.** On an explicit press only — never at activation, never as part of setup — it writes the preset's exact GitHub selection into the workspace file the Copilot harness reads for `mcpServers` (workspace-root `.mcp.json`), with the selected names in the per-server `tools` array and either the hosted URL or the vendor's local command with its documented environment variables. It keeps a copy of the content it replaced, refuses to overwrite a `github` entry this Toolkit did not write, refuses the deprecated `.vscode/mcp.json` `servers` shape because that shape has no tool-subset field, and writes no credential: the token appears only as `${GITHUB_PERSONAL_ACCESS_TOKEN}`, and a literal credential handed to it or already in the file is refused. A preset that selects no GitHub surface says so and writes nothing. What the Copilot harness then does with the file is documented vendor behaviour that has not been verified on a real host here.

**A bundle you edited can be updated without losing your edits.** A normal install or repair still never writes over a file you changed, and `Force Update Topic Skill Bundle (Archive First)` is the explicit route that may: it plans with `force: true`, lists every file it would replace with the state it measured for each — a file you changed after the Toolkit installed it, a copy the Toolkit installed at an older catalog version, a file the Toolkit never installed — says how many a normal run would preserve and the absolute folder the replaced bytes go to, and writes nothing until you accept. Ownership by another bundle is never forceable. The replaced bytes are **copied** — before any target is written, never moved, each written with `wx` and re-read and hashed, a mismatch aborting with "Nothing was overwritten." — into `.research-toolkit/bundles/archive/<bundleId>/<archiveId>/`, where `archiveId` is a UTC stamp plus a sequence (`20261117T205542Z-0001`, so two runs in the same second take different archives), each file keeping its workspace-relative path beside an `archive.json` manifest carrying the sha256 of the archived copy. `archive/index.json` lists one entry per archive, and `archive/archive.log` carries one tab-separated line per archive whose last field is the **absolute** archive path. A damaged index is rebuilt from the tree and says it was; an unknown index schema is refused and the tree is still listed; an archive is never rewritten and never deleted, and no retention policy is implemented or claimed. **Show Bundle Archive History** lists archives newest first and prints one manifest; **Restore Bundle Archive Version** stages the archived bytes, hash-verifies archive → staging → target, archives what it replaces (reason `restore`) and only then renames the copies in, and its receipt names the version restored and the version it replaced while keeping `force: false`.

**The integration bounds are settings now.** `researchStack.integrationTimeoutMs` (**80 000 ms**, allowed **40 000–300 000**) and `researchStack.integrationCooldownSeconds` (**10 s**, allowed **5–300 s**) are read in one place, `probeBounds()`, which clamps what an operator set to that range and says the clamp out loud — what was set, what ran, and why. The bounds are arithmetic on the worker's own constants: a Zotero-only check has a 34 s worst case (5 + 5 + 12 + 12 s) and the hosted side a 35 s ceiling, so 80 s covers both with room for start-up, 40 s is the smallest bound that still lets a Zotero-only check spend its full worst case including the retry that exists because a still-loading library delays the answer, and 300 s is the point past which the honest report is "these services are not answering". The bound covers the whole worker call, not one request; it cannot raise the worker's per-request limits (5 s and 12 s for Zotero, 15 s for a provider request), does not apply to component setup (`researchStack.setupTimeoutSeconds`), and does not change the worker's pacing floor of one request per second. The cooldown is measured from the end of a finished check and is the same number the card counts down and a refusal names. The 0.3.12 release notes and the packaged worker README claimed a timeout setting had been added in 0.3.12; in 0.3.12 the values were literals in `extension/integrationprobe.js` (`80_000` and `10_000`). In 0.3.14 the setting exists.

**A rollback now says what its check proves.** `Roll back managed runtime` reports the checker release and the runtime release it verified, and states which of the two claims the pairing supports: when they differ, that the older interpreter still passes **this release's** reading check, not that the checker and the runtime were verified together.

**Four new commands.** `contributes.commands` goes 39 → **43**: **Force Update Topic Skill Bundle (Archive First)**, **Show Bundle Archive History**, **Restore Bundle Archive Version** and **Configure Preset Tools for Copilot**. All four are Command Palette commands and all four now have a control in the corpus-and-bundle row of the control panel (`extension/ui.js`), labelled **Force-update topic bundle where a file differs**, **Show bundle archive history**, **Restore an archived bundle version** and **Select the GitHub tools this preset offers Copilot** (`extension/ui.js`). Panel behaviour is proven through `extension/test/harness.js` and the panel check, not through a live VS Code run.

**Measured for this release so far, on the Linux build host, as package results rather than a gate run:** the new Python cases `tests/test_vector_retrieval.py` (17) and `tests/test_lab_state.py` (9) plus renegotiated cases in `tests/test_records.py`, `tests/test_lab_server.py`, `tests/test_migration.py`, `tests/test_workspace.py` and `tests/test_stdio.py` (table count 8 → 9, which is what an additive table does); `node --test test/bundles.test.js` **29 pass / 0 fail**; `npm run test:panel` **7 assertions / 7 pass**; the integration-settings package **88 / 88** in its own suites; the rollback package **19 / 19** in `test/runtime.test.js`. `npm test` for the whole suite and `uv run --locked pytest -q` for the whole Python suite were last reported with failures outside the package that reported them, in files another package was still editing; the full-suite figures for a cut 0.3.14 have not been produced, and neither have `npm run verify-package`, `npm run check:payload`, the artifact's member count and packed/unpacked bytes, or its sha256. See `specs/phase-15-hybrid-retrieval-presets-bundles/` for the package notes and `implementation-P7-docs.md` for what was corrected where.

**What this release does not claim.** `extension/components.json` still declares five components `kind: "planned"` — **Qdrant local service, a CPU embedding runtime and model, a DuckDB record store, Playwright browser capability, and institutional provider adapters** — and this release does not change that: the vectors 0.3.14 stores are the Toolkit's own lexical signature, not an embedding model, and not a vector database. ## 0.3.13 — 14 November 2026 · Zotero work lives in the Toolkit's own worker, with the dry run and the backup built in

An operator's brief about their own Zotero 10.0.8 library (93 items, 37 with a DOI, 0 collections, 0 tags, 0 saved searches) is the source of every number below. It is kept as a tracked artifact in `evidence/realhost-2026-11-14/`, with its limits stated: one library, no write executed against it, no log from that host held here.

**The Zotero surface is two verbs instead of three tools, and the Toolkit's own worker does the work.** `zotero_library` carries every read — `status`, `collections`, `item`, `search`, `fulltext`, `export` — and `zotero_write` carries the gated write — `preview`, `snapshot`, `apply`, `journal`, `undo`. No third-party Zotero MCP server, no external binary, nothing installed on your behalf. `zotero_collections`, `zotero_item` and the old `search` name are still registered, but **only** when the configuration is a hand-written MCP entry rather than a managed preset, so a 0.3.12 configuration keeps working and a managed preset never gets a duplicate tool.

- **A write is planned before it is sent, and the plan is what you see.** `preview` returns the exact request body, the HTTP method, the fields that will change, the values they hold now, and the version guard it would send — and sends nothing. `apply` refuses without both a key Zotero issued to you and the literal confirmation `write-to-zotero`, and it refuses before Zotero is asked, so Zotero never answers 401 for a Toolkit that was never allowed to write.
- **The backup is not a step you have to remember.** Before the first change, the library is copied into `.research-toolkit/zotero-snapshots/` in your workspace. The values a write replaced are recorded in `.research-toolkit/zotero-journal/`, and `undo` replays them. An item Zotero reports as moved on is refused by `undo` rather than overwritten, and a journal that would not fit in its 4 KiB budget says which entries it dropped instead of silently truncating.
- **Measured write behaviour, honoured.** A write with no `If-Unmodified-Since-Version` is answered **428 Precondition Required**; a write whose version another change already moved is answered **412 Precondition Failed**; a write with no authorized key is answered **401** with `WWW-Authenticate: Zotero-API-Key realm="Zotero Local API"`. The Toolkit reads the version, plans against it, and stops on a conflict.
- **No delete, no merge.** `delete`, `delete_item`, `merge` and `duplicate_check` are refused by name before any request. Zotero's `server_localAPI.js` exposes no duplicate-detection and no merge endpoint, so a merge would be a guess about which item survives, and a delete has no restore.
- **A RIS file is checked before Zotero sees it.** An import that returned HTTP success on 14 November 2026 created **156 items, 61 of them empty**. `prepare_zotero_import` now runs the same structural validation over the text it generated and refuses to write a file that fails it (`RIS_INVALID`), and the theological-research skill bundle ships `scripts/validate_ris.py` for a file you wrote by hand: record count, malformed lines, repeated non-repeatable tags, unknown tags, a record with neither author nor title, a record with no identifier (a warning, not a defect to discard), and a warning on every `TY  - GEN`.
- **`TY - GEN` no longer arrives as a journal article.** `to_ris` emits `STAT` for a code of canon law or a conciliar and magisterial text, `RPRT` for a report, `THES` for a dissertation, `CHAP` and `BOOK` for parts of a book. The generator now passes its own validator; until this release it did not, because `rstrip()` stripped the trailing space off the final `ER  - ` line and the shipped test had pinned the defective output.
- **Status goes where it can be found again.** `KW` becomes a filterable tag; `N1` becomes a child note that no search can filter on. Access status and topic therefore go in `KW`, from the reviewed vocabulary in `references/zotero-vocabulary.md` (`access/`, `topic/`, `type/`, `status/`), and `zotero_write` refuses a tag outside it.
- **Full text is read, not downloaded.** `zotero_library(fulltext)` reads the text Zotero itself has indexed, per item and through the index endpoint. That endpoint answers **400** without `since`, so the Toolkit always sends it, and a zero answer is reported as *no match for this probe word* — never as *the index is empty*.
- **Export says what it keeps.** `csljson`, `bibtex`, `biblatex` and `csv` are answered; `markdown` and `counts` were answered with **400** in the build measured, so an unsupported format is refused before the request is made and a Markdown bibliography is generated from your records. CSL-JSON carries neither `extra` nor tags, so the result names `accessLabelsInExport` per format instead of letting you discover it after the import.
- **A status report says what it could not read.** `zotero_library(status)` lists the endpoints it actually got an answer from, the counts Zotero reported, and whether a write key is present. A library it could not read is reported as unknown, not as "not empty", and one refused endpoint does not discard the answers the others gave.
- **A write key is yours, and it stays in VS Code's secret storage.** New command **Research Toolkit: Store the Zotero Write Key** stores or removes a key Zotero issued in its own authorization dialog. The Toolkit never opens that dialog, never accepts the consent for you, never reads Zotero's `localAPIKeys.json`, never prints the key, and injects it only into the environment of the server that serves `zotero_write`. Reading needs no key.
- **The tool budget held.** 20 preset-selectable verbs across the three managed servers; every preset at or below 12 toolkit tools; the widest preset **Full research workflow** at **9 toolkit tools + 91 external = 100**, 28 tools of headroom under the 128-tool Copilot ceiling. `zotero_write` appears in exactly one goal preset — **Zotero handoff** — and in no package default. `all` registers 23 tools, which is the unmanaged surface, not a preset.
  - **Corrected in 0.3.14, kept here where it was written.** Three statements in this bullet were not true when they were published. (a) The widest preset is misnamed: `research-workflow` was **11 toolkit tools with zero external tools**; the 9 + 91 = 100 surface was `research-lab-max`.
