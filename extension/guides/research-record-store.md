# Research record store

Keep claims and their evidence links in one local, inspectable file.

## Setup

The **Corpus index and record store** component step (Full package) creates `.research-toolkit/store/research.sqlite3` with the reviewed schema version 3: `meta`, `sources`, `source_versions`, `chunks`, `claims`, `claim_evidence`, `claim_events` and `index_runs` — eight tables, and SQLite's own internals are not reported as part of the schema. The store component serves ten verbs: `index_corpus`, `unindex_corpus`, `search_corpus`, `evidence_read`, `verify_sources`, `claims_read`, `claims_write`, `claims_export`, `store_status` and `store_maintenance`. The **Index, search and record claims** preset exposes all ten; the **Full research workflow** preset (the Full default) exposes `index_corpus`, `search_corpus`, `evidence_read`, `claims_read` and `claims_write`. A store written by schema version 1 or 2 is migrated by the component step: the migration only adds — the `index_runs` table and the provenance and freshness columns — and rows carried over from an older store are labelled `legacy` and `unchecked` rather than given a verification they never had. A store from a newer schema is refused rather than relabelled, and reading an unmigrated store names `STORE_SCHEMA_UPGRADE_REQUIRED` instead of migrating it silently. The store is a workspace file: it is not packaged in the VSIX, not shared between workspaces, and it is ignored by the bootstrap workspace's `.gitignore` because it holds copied source text.

## First task and readiness

Write a claim with `claims_write` and link it to chunk ids already in the index (`evidence_chunk_ids: ["<chunk_id>"]`, optionally with `evidence_role` and `evidence_rationale`), then read it back with `claims_read`: every link reports `resolvable`, `current` and `stale`, and the claim carries its edit history. `claims_write` with a `claim_id` patches that claim instead of creating a duplicate, and an `idempotency_key` makes a retried write return the original. `verify_sources` is what separates the indexed version from the file you have now: it re-reads each indexed source, compares its hash with the stored version, and records `verified`, `changed`, `missing` or `inaccessible` with the time of the check; it reads your files and writes nothing to them. `claims_export` turns stored claims into report references only when the named file still exists with the recorded hash, and by default it drops references whose source is stale or unverified and reports how many it dropped — `include_stale: true` and `include_unverified: true` put them back when you want to see them. `store_status` reports source, chunk and claim counts, the index fingerprint and the freshness of each source; `store_maintenance` with `action: "backup"` writes a validated snapshot to a new file under `.research-toolkit/store/backups/` (never overwriting an earlier one, and working on a store that has not been migrated yet), and `action: "restore"` stages a candidate that only becomes the live store after you confirm it, preserving the previous one. Ready means the reading check created a claim, linked it to a stored chunk, resolved the evidence, verified the indexed sources against the files on disk, exported it, read it back, created a backup, staged a restore without activating it, and refused an unconfirmed vacuum.

## Troubleshooting and limits

`EVIDENCE_NOT_FOUND` means the chunk id is not in the index — run `index_corpus` first. `CLAIM_NOT_FOUND` means the id does not exist yet; create it. `CONFIRM_REQUIRED` blocks `vacuum` until you pass `confirm: true` after reviewing `status`. `STORE_SCHEMA_UPGRADE_REQUIRED` means the store predates schema 3: run the corpus index and record store component step, which migrates it and keeps a backup available. `STORE_CHUNK_LIMIT` means the index would exceed 20 000 current chunks. Limits: 20 000 current chunks per store, 2000 claims, 2000 characters per statement, 200 evidence links per claim. Mutating actions are separated from reads so the assistant's approval UI can gate them. DuckDB, Qdrant and other engines remain unselected candidates; this store uses only the Python standard library.
