# Research Stack Toolkit

Manage package preferences, inspect components and find onboarding guides.

## Setup

Install the 0.3.14 VSIX through Extensions: Install from VSIX. Reload when requested. Open the beaker sidebar or Research Toolkit: Open Control Panel. Choose a local workspace, open **Component setup for this package** and run **Set up package components** — setup checks workspace trust, the host tools the plan needs, the managed paths and the setup lock before it writes or downloads anything — then read the **Installation status** card and run Run MCP reading check or Read selected PDF / DOCX. On the Full package, **Index Selected PDF / DOCX / Text Sources** indexes your own sources into the research store and **Verify Source Freshness** re-hashes the indexed sources against the files present now. **Install Topic Skill Bundle**, **Repair Topic Skill Bundle** and **Show Topic Bundle Status** work on the reviewed bundles in `extension/bundles/catalog.json`. If a step was recorded but the files it produced are gone, **Update or repair component steps** re-runs it; **Refresh component status** re-verifies the produced files without running the MCP check; **Retry Failed Component Steps** re-runs the steps whose last attempt failed or was blocked. The version comes from the running extension manifest, not the selected package. Save a package preference and a tools preset; the preset selects the goal-shaped tool surface your assistant is offered. The plan the panel runs is declared in `components.json`, each completed step is recorded in `.research-toolkit/managed/worker-0.3.14/installation.json`, and every attempt is recorded in `.research-toolkit/logs/`.

## First task and readiness

Save your package preference, select a research folder and run Check component status, then Check components. The **Installation status** card names the outcome of the last component setup — `Installation complete — N component step(s) verified.`, `Installation incomplete — N step(s) verified, M need attention (step ids).`, `Installation failed — <step>: <error>.`, `Setup blocked — <reason>.`, `Setup cancelled — N step(s) already completed were kept.` or `No component setup has run in this workspace yet` — with a row per step (status, duration, attempts, exit code and error), the host tools setup resolved, and the action that clears the failing or blocked step. It is read from `.research-toolkit/logs/last-setup.json`, so a reopened panel or a reloaded window shows the same verdict. **Open Setup Log** opens the newest attempt log; **Copy Installation Diagnostics** copies the verdict, host tools, preflight results, per-step attempts and the log file path to the clipboard. The setup section names each step this package offers as installed, outdated, needing repair or deliberately omitted; **Update or repair component steps** re-runs the steps an earlier toolkit release recorded plus any recorded step whose produced files are missing, and **Refresh component status** re-verifies those files without running the MCP reading check. Each component row offers Install or Update where the toolkit can install it. **Diagnose tool limit** and **Copy preset summary** report the same budget from the Command Palette. Read Installation and Readiness separately. Guide opens local setup steps; Latest docs opens the maintained official source. Under Tools preset, choose the goal you are working on and open its context estimate: tool count, headroom under the 128-tool client ceiling, and the estimated size of the tool definitions. **Research Toolkit: Select Tools Preset** offers the same choice in the Command Palette.

**What the 0.3.14 controls add.** **Force Update Topic Skill Bundle (Archive First)** replaces the files of a bundle you edited after installing it, after a modal names every file it would replace, the state each one is in, and the folder the replaced bytes are copied into first; **Show Bundle Archive History** lists the archived versions newest first, with the absolute folder each one lives in; **Restore Bundle Archive Version** writes one of them back and archives what it replaced. Every archive is under `.research-toolkit/bundles/archive/<bundleId>/<stamp>-<sequence>/` — the sequence is what keeps two archives made in the same second apart — with an `index.json` and an `archive.log` whose last field is the absolute archive path, and nothing there is ever deleted. **Configure Preset Tools for Copilot** writes the GitHub tool names the selected preset chose into the workspace `.mcp.json` (`mcpServers.github`, with a per-server `tools` allow-list), asks before writing, shows both the hosted and the local entry first, keeps every server entry it did not write, copies the file it replaces under `.research-toolkit/preset-tools/`, and writes `${GITHUB_PERSONAL_ACCESS_TOKEN}` rather than a token. The record store now answers `search_corpus` with `mode`: `lexical`, `vector` or `hybrid`, and `embed_corpus` builds the vectors; `store_status` states whether the index is `not-built`, `partial`, `stale` or `ready`. Zotero and Semantic Scholar checks read `researchStack.integrationTimeoutMs` (40 000–300 000 ms, default 80 000) and `researchStack.integrationCooldownSeconds` (5–300 s, default 10) from the settings, and the card and the log report the bound actually in force.

## Troubleshooting and limits

Ready confirms this controller is running, not that every component is usable. If controls are missing, check the active VS Code profile and extension enablement. Package choices and tool presets do not install tools; a preset only changes which tools the managed workers register. Setup runs only when you start it, resumes after a cancelled or failed run, and never overwrites existing files. A step that needs another step pulls its prerequisite in and says why; when a step fails, the steps that do not depend on it continue and its dependents are reported as blocked with the step that blocked them. If uv is not found, setup is blocked before anything is written and the message names the locations searched — point `researchStack.uvPath` at the executable and reload the window. A downloading step that needs longer than the default 900 seconds is reported as timed out; `researchStack.setupTimeoutSeconds` (60–3600) raises it. **Clear Interrupted Setup Lock** removes only a lock classified as stale — older than the setup window, or older than 60 seconds with a dead owner process — and refuses a live one. A preset saved for a package that does not offer it falls back to that package's default; a preset retired in 0.3.14 keeps working for a workspace that saved it, and the panel names it as retired and says which presets replace it. Where a preset names its external tools — the three Maximum research presets and their GitHub surfaces — the count stated is the length of that name list; the names themselves are GitHub's published catalog as reviewed on 2026-11-17, not tools counted on your machine, and no estimate anywhere in the panel is presented as a measurement of a server this extension does not start. A topic bundle install reports `filesInstalled` only: `hostDiscoveryVerified` and `workflowTested` stay `false` in its receipt because this toolkit cannot observe the host's skill discovery and never runs the bundle's scripts.

**Updates & problem reports.** The panel ends with a section answering two questions an operator used to answer by hand. **Check for a newer Toolkit version** asks the VS Code Marketplace once — at most once a day, never at startup, and never when `researchStack.checkForUpdates` is off — whether a newer version of this extension is published, and reports one verdict: up to date, an update is available, this copy is newer than the published one, your VS Code is too old for the published build, nothing is published yet, or the check did not complete. VS Code updates an extension installed from the Marketplace by itself; it does **not** update one installed from a `.vsix` file, which is how earlier releases reached most people, so this check and **Update from the Marketplace** exist. The update is applied by asking VS Code to install the published `michaelprinc.research-stack-toolkit` build — the same signed path the Marketplace uses — which also returns the extension to normal automatic updating; if the editor refuses, the Toolkit opens the Marketplace page instead and says so. **Report a problem to the maintainer** writes a plain-text report — environment, package and preset, the recorded setup verdict, the last 40 lines of the setup log, up to 12 recent failures and your own note — into the extension's own storage folder, opens it and copies it to your clipboard. Absolute paths, home folders, workspace names and token-shaped strings are replaced with `<path>`, `<home>`, `<workspace>` and `<redacted>` before you see it, and the report ends with a count of what was removed. Only after that, and only if you choose it, does the Toolkit hand a short draft to your own mail program addressed to princ.michael@gmail.com. Nothing is uploaded by the Toolkit, and the full report travels as the file or the paste you already have.
