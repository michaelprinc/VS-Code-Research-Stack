# Research Stack Toolkit 0.3.13 — Zotero Work Now Lives Inside the Toolkit's Own Worker

Install the components each package actually needs from the VS Code control panel, read **one plain-language verdict for the last component setup** — what completed, what failed, and what to do next — verify real MCP reading, see actual component versions and readiness, and choose a **tools preset shaped by the goal you are working on** so your assistant is offered fewer, better-matched tools. **0.3.11 added Integrations & Accounts**: one place that detects Zotero and Semantic Scholar, asks only for the decision each service actually needs, and remembers it for every workspace in your VS Code profile. **0.3.12 was the correction pass after an operator ran 0.3.11 against a real Zotero 10 on Windows** — the readiness check reported what Zotero actually answered instead of a mystery, and it could no longer crash. **0.3.13 puts the Zotero work itself in the Toolkit's own worker**: one read verb, one gated write verb with the dry run and the backup built in, and a RIS file that is checked before Zotero ever sees it.

Start with the [onboarding walkthrough](guides/onboarding.md) or [guide hub](guides/index.md). The hub is assembled from **29 individual component guides**, each with setup, a first task, readiness interpretation, troubleshooting and a maintained official documentation link.

## What 0.3.13 adds

Everything below runs inside the Toolkit's own managed Python worker. No third-party Zotero MCP server, no external binary, no npm dependency, nothing installed on your behalf.

- **Two Zotero verbs replace three Zotero tools.** `zotero_library` reads — `status`, `collections`, `item`, `search`, `fulltext`, `export` — and `zotero_write` writes — `preview`, `snapshot`, `apply`, `journal`, `undo`. The verbs 0.3.12 shipped (`zotero_collections`, `zotero_item`, and the old `search` name) stay registered **only** for a hand-written MCP entry that still calls them, so a 0.3.12 configuration keeps working. A managed preset gets the real names and no duplicates.
- **The dry run and the backup are part of the tool, not a procedure you have to remember.** `preview` returns the exact request body and the version guard it would send, and sends nothing. `apply` refuses without both a key Zotero issued to you and the literal confirmation `write-to-zotero`, and it refuses before Zotero is asked. Before the first change the library is copied into `.research-toolkit/zotero-snapshots/`; the values a write replaced are recorded in `.research-toolkit/zotero-journal/`, and `undo` replays them. An item Zotero reports as moved on is refused by `undo` rather than overwritten.
- **No delete, and no merge.** `delete`, `delete_item`, `merge` and `duplicate_check` are refused by name before any request: a delete has no restore, and Zotero's local API has no duplicate-detection and no merge endpoint, so a merge would be a guess about which item survives.
- **Every write carries the version guard Zotero demands.** Measured on a real Zotero 10.0.8: a write with no `If-Unmodified-Since-Version` is answered **428**, and a write whose version another change already moved is answered **412**. The Toolkit reads the version, plans against it, and stops on a conflict instead of overwriting what changed underneath it.
- **The tool budget did not grow.** The Toolkit still offers 20 preset-selectable verbs across its three servers, every preset stays at or below 12 toolkit tools, and the widest preset — **Full research workflow** — now carries **9 toolkit tools plus 91 external tools = 100**, leaving 28 tools of headroom under the 128-tool Copilot ceiling. Consolidating Zotero bought capability, not tool count: three verbs now carry ten read capabilities and seven write operations.
- **A RIS file is checked before Zotero sees it.** `prepare_zotero_import` validates its own output and refuses to write a file that fails (`RIS_INVALID`), and the theological-research skill bundle ships `scripts/validate_ris.py` for a file you wrote by hand. The reason is measured, not theoretical: an import that returned HTTP success on 14 November 2026 created **156 items, 61 of them empty**.
- **`TY - GEN` no longer arrives as a journal article.** The Toolkit now emits `STAT` for a code of canon law or a conciliar and magisterial text, `RPRT` for a report, `THES` for a dissertation, `CHAP` and `BOOK` for parts of a book. The validator warns on every `GEN` it finds.
- **Status goes where it can be found again.** Access status and topic go in `KW`, which Zotero turns into filterable tags, never in `N1`, which becomes an unfilterable child note. `zotero_write` accepts tags only from the reviewed vocabulary in the bundle (`access/`, `topic/`, `type/`, `status/`) and refuses anything else.
- **Full text is read, not downloaded.** `zotero_library(fulltext)` reads the text Zotero itself has indexed, per item and through the index endpoint, which Zotero answers with **400** unless the request carries `since`. A zero answer is reported as *no match for this word*, never as *the index is empty*.
- **Export says what it keeps.** `csljson`, `bibtex`, `biblatex` and `csv` are answered by Zotero; `markdown` and `counts` are answered with 400 in the build measured, so the Toolkit refuses them before asking and a Markdown bibliography is generated from your records. CSL-JSON carries neither `extra` nor tags, so the tool reports `accessLabelsInExport` per format instead of letting you discover it after the import.
- **A write key is yours, and it stays in VS Code's secret storage.** **Research Toolkit: Store the Zotero Write Key** stores a key Zotero issued in its own authorization dialog. The Toolkit never opens that dialog, never accepts that consent for you, never reads Zotero's own `localAPIKeys.json`, never prints the key, and hands it only to the worker that serves `zotero_write`. Reading needs no key at all.
- **A real host confirmed the earlier tools.** An operator's Zotero 10.0.8 library — 93 items, 37 with a DOI, 0 collections, 0 tags, 0 saved searches — confirmed the loopback read, the RIS preparation Zotero accepted, and the readiness check that distinguishes "Zotero refuses local clients" from "nothing is listening". The brief and its limits are recorded in `evidence/realhost-2026-11-14/`. **G1–G4 remain open**: that run exercised the tools the gates ask for, but a gate closes on its receipts, and the receipts for a reference-host install, an Extension Host and a rendered window have still not been produced.

## What 0.3.12 adds

0.3.12 changes no feature surface. It is the correction pass after an operator installed Zotero 10 on Windows, pressed **Check now**, and got a failure the Toolkit could not describe.

- **The check reports what Zotero answered.** The receipt now carries the HTTP status and a short, scrubbed line of the server's own words — for example `403 Forbidden Local API is not enabled` or `root 200 Zotero-API-Version 3 Zotero-Server-ID sPMHtLD6HHBd HEAD 200`. A 400, a 401, a 404 and a 403 that is *not* about the setting are four different answers with four different sentences, and only the one that is about the setting tells you to change a setting.
- **The check waits as long as Zotero actually needs.** Zotero answers its local API only after your library has finished loading, and Zotero's own Connector allows 15 seconds for one request. The stages now wait 5, 12 and 3 seconds instead of 2, and the library listing is asked twice before anything is reported.
- **The check can no longer crash.** A server that closes the connection without answering used to fail the whole check, so the other service was never assessed. Each service is now assessed on its own.
- **A refused port is not an absent Zotero.** Zotero opens 23119 late in its startup, and if another program already holds it Zotero starts no HTTP server at all. "Nothing answered" and "no Zotero" are now different sentences.
- **`Check now` answers, and is not offered where it cannot run.** It used to report "Done." while the verdict went only to the Output channel. Now the verdict sentence names the service and its state; where the check cannot run, the button shows the reason and the remaining wait instead of throwing an error about package components.
- **One check at a time, and a 10-second shared window instead of 30.** Three of the five ways a check starts bypassed the lock. Opening *Integrations & Accounts* no longer holds it for 20 seconds.
- **The guided Semantic Scholar flow describes the path that exists.** Its modal told you to press *"I already have a key"* — a button that appears only after the integration is activated, which is correct, because a key must not be stored before you have accepted the provider's terms. It now says to activate first.
- **A stale installation fact is evidence, not a permanent veto.** A confirmation older than the Toolkit's seven-day window re-opens *Guided installation* and *I have installed Zotero — check it now*.
- **A panel button that is unavailable says so and announces it** — including read-only controls, which previously could be marked unavailable and still stay pressable.

See **Zotero has one setting that decides whether the Toolkit can read it** below for the setting itself, the twelve-second library wait and the taken-port case.

Several VS Code windows share one check budget, so they do not each fire a provider request. The Toolkit cannot set it for you and never tries to. When that is the reason a check failed, the card says so and names the setting rather than reporting a mystery. Two other facts worth knowing before you press **Check now**: Zotero answers its local API only after your library has finished loading, so the first check after starting Zotero can take longer than the ones after it — the Toolkit waits up to twelve seconds for the library listing and asks once more before it reports anything; and if another program already holds port 23119, Zotero starts no HTTP server at all rather than choosing a different port, which reads as "nothing answered" rather than "Zotero is absent". If a check on your machine is hard to explain, `scripts/zotero_local_check.py` in the repository asks the same loopback requests and prints what Zotero actually said, with no Toolkit involved. If your environment already carries `SEMANTIC_SCHOLAR_API_KEY`, `SEMANTIC_SCHOLAR_LICENSE_ACKNOWLEDGED`, `OPENALEX_API_KEY`, `CROSSREF_MAILTO` or `CROSSREF_PLUS_API_TOKEN`, the panel names the variables it found — never their values — and leaves them alone.

**Your existing configuration is reported, not replaced.** If your environment already carries `SEMANTIC_SCHOLAR_API_KEY`, `SEMANTIC_SCHOLAR_LICENSE_ACKNOWLEDGED`, `OPENALEX_API_KEY`, `CROSSREF_MAILTO` or `CROSSREF_PLUS_API_TOKEN`, the panel names the variables it found — never their values — and leaves them alone.

**The Toolkit now keeps a small amount of state outside your project, and this page says exactly what is in it.** The research worker writes a request budget, a small response cache and an installation fact into one folder in your OS user's application-data location, so that several Toolkit processes and several VS Code windows stop stampeding the same service. They hold request timing and a classification of what was found — never a key, never a token, never a URL, never a path to your files. See **What the Toolkit writes, and where**.

## What 0.3.10 adds

Everything below is covered by the automated suites on this Linux development host. Nothing in this release has been run on a Windows host or in a live VS Code session, and no statement below depends on one.

**The Toolkit can tell you a newer version exists.** VS Code updates an extension installed from the Marketplace by itself. It does **not** update an extension installed from a local `.vsix` file — VS Code marks that install as pinned and leaves it where you put it — and every release of this Toolkit since 0.3.0 reached people as a `.vsix` file. **Check for a newer Toolkit version** asks the Marketplace one question and answers it in the panel: up to date, an update is available, this copy is newer than the published one, your VS Code is too old for the published build, nothing is published yet, or the check did not complete. **Update from the Marketplace** then asks VS Code to install the published build through the Marketplace — the same signed path any extension update takes — which also returns the Toolkit to normal automatic updating. If the editor refuses, the Toolkit opens the Marketplace page and says so.

**One request, disclosed and switchable.** The check is a single HTTPS GET to `marketplace.visualstudio.com`, at most once a day, never at startup, with an 8-second timeout and a 64 KB response cap. The URL contains the publisher id and the extension name, both already public in the manifest: no workspace path, no file name, no user identity, no diagnostics. `researchStack.checkForUpdates` (on by default) switches it off, and with it off this extension contacts no online service at all. It is the only packaged JavaScript in the release that can open a socket, and the packaging audit names it, counts its request sites and re-checks its timeout, byte cap and cooldown on the shipped bytes.

**A problem report you read before anyone else does.** **Report a problem to the maintainer** collects the environment (VS Code, platform, Node, install kind), the package and preset, the recorded setup verdict, the last 40 lines of the setup log, up to 12 failures seen in this window and a note you type, and writes it as a plain-text file in the extension's own storage folder. Absolute paths, home directories, workspace folder names and token-shaped strings are replaced with `<path>`, `<home>`, `<workspace>` and `<redacted>` — including inside your own note and inside the log lines — and the report ends with a count of what it removed. The file is opened and copied to your clipboard. Only after that, and only after you confirm in a modal, does the Toolkit hand a short draft to your own mail program addressed to `princ.michael@gmail.com`. Nothing is uploaded, no message is sent by the extension, and the full report reaches the maintainer as the file or the paste you already have.

**A Marketplace tile icon.** The manifest now declares `media/toolkit.png` (256×256 PNG, generated from the reviewed `media/toolkit.svg` by `scripts/make_icon.js` and byte-reproducible). The Marketplace rejects an SVG icon outright, so the activity-bar icon stays SVG and the tile gets a PNG. The manifest also declares `bugs.url` and `bugs.email`, so the Marketplace page and **Report a Problem** point at the same place.

## What 0.3.9 adds

Everything below is covered by the automated suites on this Linux development host. Nothing in that release has been run on a Windows host or in a live VS Code session, and no statement below depends on one.

**PDF and DOCX sources can be indexed directly.** `index_corpus` accepts explicitly selected workspace PDF and DOCX files beside Markdown and text. A PDF chunk carries the page number it came from and its character offsets inside that page's extracted text; a DOCX chunk carries its ordered paragraph or table-row item. A chunk never crosses a page or an item. The Markdown/text chunker `paragraph-window-v1` is unchanged, so chunk ids and locators written by an earlier release still resolve; PDF and DOCX get their own chunker identities (`pdf-page-window-v1`, `docx-item-window-v1`).

**Each indexed source states what was actually read.** The stored record carries the workspace-relative path, the source-byte SHA-256, the byte size, the kind, the parser and its version (`pypdf`, `python-docx`), unit counts, coverage (units read, units holding text, empty units, failed units, batches), warnings, and one outcome: `complete`, `partial` or `failed`. A source whose bytes change while it is being read is refused with `SOURCE_CHANGED_DURING_INDEX`.

**The indexed version and the present file are separate facts.** `verify_sources` is the tenth verb on the store server and the only verb that may call a source `verified`. The states are `verified`, `changed`, `missing`, `inaccessible` and `unchecked`. `index_corpus` gained `accept_partial` (the CLI's `--accept-partial`); a partial or failed read does not replace an indexed version unless the operator accepts it, and the control-panel index command offers no such acceptance — a partial source is reported as refused and left at its previous version. One index call is one transaction, and every call leaves exactly one row in the new `index_runs` table. Claim exports exclude stale and unverified references by default and count them (`excludedStaleReferences`, `excludedUnverifiedReferences`, `uncheckedReferences`).

**The store is at schema 3, reached by an additive 2→3 migration.** A migrated row is labelled `legacy` / `unchecked` and is never back-filled: 0.3.8 did not record what 0.3.9 now records, and the toolkit does not invent it. Existing chunk ids are unchanged. `backup` works on a store that has not been migrated yet. `restore` stages a validated candidate and only `confirm=true` activates it, preserving the previous store in a named file.

**Topic skill bundles.** The extension ships a reviewed built-in catalog (`extension/bundles/catalog.json`, generated by `scripts/build_bundle_catalog.py`) and five new actions: **Index Selected PDF / DOCX / Text Sources**, **Verify Source Freshness**, **Install Topic Skill Bundle**, **Repair Topic Skill Bundle** and **Show Topic Bundle Status**. A bundle installs under `.github/skills/<skill-id>/…`. Every file is copied to a staging directory and hashed there against the catalog before anything moves into the workspace; a file you edited is left exactly as it is; nothing is ever deleted; a skill owned by another bundle is neither written nor removed. The install writes a receipt at `.research-toolkit/bundles/<bundle-id>.json`. The receipt separates three claims and never merges them: `filesInstalled` (verified by hash), `hostDiscoveryVerified` (**false** — the toolkit cannot observe this host's skill discovery from the machine that ran the install) and `workflowTested` (**false**). "Files installed" is the only status an automated install may claim.

**The first bundle is theological-research 2.0** (11 files). Its licence is **unresolved** — author consent is required before it may be published — so the catalog records `publishable: false`, and the packaging audit refuses any bundle whose licence is unresolved while the catalog calls it publishable. Its adaptations from the author's working copy are recorded in `docs/implementation/phase-9-document-ingestion/bundle-notes.md`; read that file rather than taking the bundle's presence as evidence about its contents. The second bundle is **document-corpus-bridge 2.0** (1 file), the workflow for indexing PDF and DOCX and citing them by page or item. It replaces the 0.3.8-era skill that told the assistant to stage derived Markdown because the indexer refused those formats; that text is kept only as the fallback for files the indexer genuinely refuses. It is toolkit-authored, and the toolkit repository is UNLICENSED, so it too is packaged but not publishable.

**Unchanged exclusions.** No OCR, no scanned-image recognition, no vector or embedding search, no background ingestion, no external account provisioning, no automatic acquisition of papers. The toolkit still does not install uv, does not run setup silently or in the background, and does not execute notebook kernels.

## What 0.3.8 fixes

If you installed 0.3.7 in a workspace whose name contains characters your Windows console cannot represent — for example `k:\Soukromé_aktivity\Bankovní účet SVJ ČSA368` — and **Corpus index and record store** ended with **"python.exe -I failed with exit code 2: `{"error": "'charmap' codec can't encode character '\u010d' … character maps to <undefined>"}`"**, this release is for you. The record store **was** created. What failed was the worker's ability to *report* that it had been created: the report contained your workspace path, and the child process had been handed your system's console encoding (cp1252 on an English-locale Windows 11), which has no byte for `č`. Your workspace, your Python, your uv and your network were not at fault.

* **The worker states its own output encoding.** Every Python child this toolkit starts is started with UTF-8 standard streams, and the worker restates that promise itself before it writes anything — so it holds however the process was launched, including a managed runtime left behind by an older toolkit release that this one can still activate.
* **The receipt the panel parses is ASCII-only.** A workspace path in a report can no longer be garbled or crash the command that prints it. `ČSA368` appears as `ČSA368` in the raw JSON and as `ČSA368` in the panel, which parses the JSON.
* **A report the extension cannot read is refused, not recorded.** If a worker's report arrives as bytes that are not valid UTF-8, the step is reported as a named failure that says the step was not recorded and that re-running it is safe — instead of recording a store path containing replacement characters that the panel would later fail to find.
* **A text-encoding failure is named as one.** The step now says it is a text-encoding problem and explicitly not a network, proxy or interpreter problem, and it is never retried as if it were a transport failure.
* **Every command the worker answers is covered**, not only the store step: `inspect`, `init`, `add-recommended`, `read` and `export-bundle`, and the error sentences that name a Czech path.
* **The MCP servers the editor starts carry the same flags**, so the guarantee lives in this toolkit rather than only in the MCP library's transport.

## What 0.3.7 fixed

If you installed 0.3.6 and **Set up package components** ended with **"Installation incomplete — 1 step(s) verified, 1 need attention (Isolated locked worker (Python 3.12))"**, and the step log said (that release fixed it; the record below is kept as history): **"uv.exe sync failed with exit code 1: … The lockfile at `uv.lock` needs to be updated, but `--locked` was provided"**, this release is for you. The cause was inside the toolkit's own build: 0.3.6 shipped a locked dependency file that still recorded an older version of the worker project than the project file beside it, and uv refuses such a pair before it installs anything. Your workspace, your network, your proxy and your Python were not at fault.

* **A bad build is refused before anything runs.** The extension compares the dependency lock and the project file it ships, inside itself, before it takes the setup lock, starts a process or writes a file. If they disagree it stops with *"This toolkit build ships a locked dependency file that does not match its own project file: … No process ran and no file was written. Reinstall the Research Stack Toolkit VSIX; this is a defect in the toolkit build, not in this workspace."*
* **A lock mismatch is explained in plain language.** When a host's uv still refuses the shipped lock, the step names it as a lockfile disagreement — explicitly not a network, proxy or interpreter problem — instead of an exit-code line you had to interpret yourself. The toolkit then compares the two files itself and says which side disagrees: a broken toolkit build, or this host's uv refusing a lockfile the toolkit reads as current.
* **One reviewed retry, and it says so.** The worker step installs the locked set first. Only when uv's own refusal is recognised as a lock mismatch does the toolkit retry exactly once with the reviewed fallback that installs the packages the shipped lock pins, without rewriting the lock. That fallback is recorded in the step evidence, in the setup log and in **Copy Installation Diagnostics**, so a fallback install is never presented as a clean one. The toolkit never re-locks a managed runtime and never installs without a lock.
* **The shipped lock was regenerated, not hand-edited** (uv 0.13.6): the same 40 resolved packages and the same 39 third-party version pins, with only the worker project's own recorded version corrected to 0.3.7.
* **A stray shell variable can no longer change what setup does.** The variables that would alter the reviewed uv command (`UV_INDEX`, `UV_INDEX_URL`, `UV_DEFAULT_INDEX`, `UV_EXTRA_INDEX_URL`, `UV_FIND_LINKS`, `UV_NO_INDEX`, `UV_LOCKED`, `UV_FROZEN`, `UV_UPGRADE`, `UV_NO_SYNC`, `UV_OFFLINE`, `UV_NO_DEV`, `UV_SYSTEM_PYTHON`, `UV_EXCLUDE_NEWER`, `UV_PYTHON_PREFERENCE`) are removed before the reviewed environment is applied, whatever spelling the host used — on Windows the same variable can arrive as `Uv_Index_Url` or `uv_locked`.
* **The build refuses this class of defect.** The worker bundle builder, the packaged-VSX audit and the test suite all compare the shipped lock with the shipped project file, so a stale pair cannot leave the toolkit again.

2. Click the **Research Toolkit** beaker icon in the Activity Bar, then **Open Control Panel**. You can also click the **Research: …** status-bar item or run **Research Toolkit: Open Control Panel** from the Command Palette.

4. In **Component setup for this package**, review the steps this package offers and click **Set up package components**. Setup starts with a preflight — workspace trust, a local desktop workspace, the host tools the plan needs, the managed paths and the setup lock — and nothing is written or downloaded until that preflight passes. 5. Read the **Installation status** card. It names the overall outcome of the last component setup and each step, with the failing or blocked step, its exit code where there was one, and the action that clears it. 6. Click **Read selected PDF / DOCX** to verify a source inside the workspace and see text, locators and its hash. 7. Use **Guide** for its bundled setup steps or **Latest docs** for current official instructions. Choose and save a package preference and a tools preset independently of installation.
8. Under **Tools preset**, pick the goal you are working on, open **Context usage and tools in the selected preset**, and save. The preset changes which tools your assistant is offered; it installs nothing.

Your existing 0.2.0/0.3.0 package and interface preferences are retained. Preferences belong to the active VS Code user profile. Component observations are scoped to the selected folder/current editor and retained in this session with a check timestamp; rerun checks after environment changes or restart.

## Component setup, step by step

The install plan is declarative: `components.json` (schemaVersion 2) states, for every component, who installs it, which step provides it, how it is verified and what you should do next. The extension runs only the steps your package needs, in order, and records each one in `.research-toolkit/managed/worker-0.3.13/installation.json`.

| Package | Steps offered | What they install |
|---|---|---|
| Basic | Isolated document worker | Locked Python 3.12 worker environment plus the five document tools (`read_document`, `read_text_source`, `search_local_text`, `write_markdown`, `write_docx`), verified by real MCP reading checks |
| Recommended Research | Worker, reviewed research overlay, notebook analysis environment (optional) | Adds the scholarly metadata/Zotero adapter, the reviewed `.github/skills`, profile and `research/` files, and a locked `notebooks/analysis` environment |
| Full | Worker, research overlay, notebook environment (optional), corpus index and record store | Adds the workspace corpus index and SQLite research record store under `.research-toolkit/store/` (schema 3: sources, source versions, chunks, claims, evidence links, claim events, index runs) |

* **Set up package components** runs the missing steps. **Update or repair component steps** re-runs the steps an earlier toolkit release recorded **and** the steps this release recorded but whose produced files are gone. **Retry Failed Component Steps** re-runs the steps whose last attempt failed or was blocked, together with the steps those failures blocked, and keeps the work that completed. **Check component status** runs the bounded host/library checks; **Refresh component status** re-reads the plan and re-verifies the produced files without running the functional MCP check.
* A step is reported as `installed` only when its produced files are still present. A recorded step whose files were deleted is reported as **needs repair** and is re-run, not presented as complete.
* The **Installation status** card names the outcome of the last component setup and each step, in one of these words: `Installation complete — N component step(s) verified.`, `Installation incomplete — N step(s) verified, M need attention (step ids).`, `Installation failed — <step>: <error>.`, `Setup blocked — <reason>.`, `Setup cancelled — N step(s) already completed were kept.` or `No component setup has run in this workspace yet`. A success verdict is only given when the files each step was supposed to produce were re-checked on disk after the run; for the worker step that means `.venv/bin/python` on Linux/macOS, `.venv/Scripts/python.exe` on Windows, and the managed `src/research_stack/mcp_server.py`.
* Setup runs a preflight before any component command: workspace trust, a local (non-remote) desktop workspace, the required host tools from the component registry, the managed path being a real directory rather than a link, a writable workspace, and the setup-lock state. A blocked preflight writes a status record with the outcome `blocked` and runs nothing. Before the plan touches anything, the extension also compares the dependency lock it ships with the project file it ships beside it: a build whose pair disagrees is refused as a defect in the toolkit build, with no process started and no file written.
* `uv` is resolved in a fixed order: `researchStack.uvPath`, then absolute `PATH` entries, then the documented install locations for the platform (Windows: `%USERPROFILE%\.local\bin`, `%LOCALAPPDATA%\Programs\uv`, `%APPDATA%\Python\Python312\Scripts`, `%APPDATA%\Python\Scripts`, scoop shims, WinGet Links and `C:\Program Files\uv`; macOS/Linux: `/usr/local/bin`, `/opt/homebrew/bin`, `/usr/bin`, `~/.local/bin`, `~/.cargo/bin` and `$XDG_BIN_HOME`), then the workspace's managed toolkit folder. A found tool is version-probed with `uv --version`; a tool whose version command fails, or whose version is older than the registry minimum (uv 0.5.0), is reported as unusable rather than as installed. An executable inside the workspace is refused as a host tool. If uv is not found, setup is blocked before anything is written, and the message names the locations searched and the `researchStack.uvPath` remedy.
* A failing step no longer aborts the whole plan. Independent steps continue, steps that depend on the failure are recorded as `blocked` with the step that blocked them, and every attempt is recorded. A transient failure — a timeout, output over the capture limit, or network-flavoured tool output — is retried once; a launch failure (`ENOENT`), a cancellation or an explicit refusal is not retried.
* An optional step you did not install is reported as a deliberate omission, not as an unmet requirement.
* Each component row in the panel and in the sidebar has **Install** / **Update** where the toolkit can install it; rows the toolkit cannot install state who does (editor, host tool, external service, or planned).
* A step that needs another step pulls that step in and says why, instead of failing the click or half-installing: the record store needs the worker.
* Existing files are never overwritten. Overlay files are created once, hash-verified against the bundle, and classified on re-run as unchanged or **changed by you and preserved**; a linked or junctioned path is refused rather than followed.
* A cancelled or failed run leaves the completed steps recorded, so the next run resumes at the first missing step. The receipt and the active-runtime pointer are written atomically, and one setup lock covers the whole plan so two windows cannot interleave steps. A lock is classified **stale** only when it is older than the setup window, or older than 60 seconds with a dead owner process; **Clear Interrupted Setup Lock** removes only such a lock and refuses a live one.
* Two steps reach the network, and only those two: the **isolated document worker** step syncs its locked Python 3.12 environment, and the optional **notebook analysis environment** step syncs the reviewed `notebooks/analysis` project (`uv sync --locked`). Only the two locked sync steps have a fallback, and only for a recognised lock mismatch: one `uv sync --frozen` run that installs exactly what the lock pins, recorded in the step evidence and the setup log as a fallback rather than as a clean install. It runs only when the toolkit's own check of the same pair says the pair is current — a build whose pair really disagrees is refused instead. The toolkit never runs `uv lock` in a managed runtime and never runs a plain unlocked `uv sync`. No other step downloads anything, and no step starts a kernel. Both honour `researchStack.setupTimeoutSeconds` (default 900 s, allowed 60–3600 s), because a first run can fetch a managed Python 3.12 and the locked packages. Setup runs with a reviewed uv environment: pinned Python 3.12, copy link mode, no progress spinners, no user config file, and a workspace-contained project environment; the `UV_*` variables that would change what the reviewed command means are removed before those values are applied. The MCP reading check that closes the worker step honours the same bound instead of a fixed 90 s. The notebook step first classifies what is already in `notebooks/analysis` — reviewed project, compatible existing project, or neither — refuses a linked environment, and records that `ipykernel` and `matplotlib` import in the environment it created.
* Setup evidence stays in the workspace: `.research-toolkit/logs/last-setup.json` is the status record the panel reads when it reopens, and `.research-toolkit/logs/setup-<timestamp>.jsonl` is the append-only attempt log. The bootstrap workspace's `.gitignore` ignores `.research-toolkit/logs/` alongside the existing derived-data rules. **Open Setup Log** opens the newest log file, and **Copy Installation Diagnostics** copies the verdict, the host tools, the preflight results, the per-step attempts and the log file path to the clipboard.
* **Roll back managed runtime** lists the managed runtimes this workspace holds, re-verifies the candidate with the real reading check, and only then points the workspace back at it. The runtime an earlier release installed stays on disk.

## What the Toolkit writes, and where

Everything the Toolkit writes into your **project** is under `.research-toolkit/` and is described above: the managed runtimes, the corpus index, the research record store, the export bundles, and the setup logs.

0.3.11 adds a second location, because some facts are not about a project. The research worker keeps a small amount of state in **one folder in your OS user's application-data location**, under the name `research-stack-toolkit/`:

* **Windows** — `%LOCALAPPDATA%\research-stack-toolkit\`
* **macOS** — `~/Library/Application Support/research-stack-toolkit/`
* **Linux** — `$XDG_DATA_HOME/research-stack-toolkit/`, or `~/.local/share/research-stack-toolkit/` when that variable is unset
* If no per-user directory can be resolved, the Toolkit falls back to the session temp directory and **says so** — the state then is not shared between workspaces, and the diagnostic names the fallback rather than hiding it.

What is in that folder, and what each file may contain:

| File | What it holds | What it never holds |
|---|---|---|
| `budget-<provider>.json` | Four numbers: where the current request window started, how many permits were used, when the next request may start, and until when the provider is being waited out. A short-lived lock file with the same name plus `.lock` guards the write and is taken over after 30 seconds if a process died holding it. | Anything about your documents, your identity, your key, or your paths. |
| `cache-<provider>.json` | Provider metadata for answers already fetched, so the same question is not asked twice. Bounded at **16 entries of at most 32 768 bytes each** (about 0.5 MB worst case) and reused for at most 15 minutes. | A key, a token, a URL, a workspace path, or a path to any file of yours. |
| `integration-facts.json` | Whether Zotero was found on this machine, how the Toolkit classified what it found, the platform, and the time it looked. Capped at **8 192 bytes**; a write that would exceed the cap is **refused**, not truncated. | A secret, a key-shaped or token-shaped string, a workspace path, or a path to your Zotero library. A value shaped like one of those is refused and the refusal names the rule it broke — without repeating the value. Semantic Scholar never appears in this file: it is a hosted service with nothing on your machine to find. |

Why these three live outside your project: they are shared. The budget is what stops two Toolkit processes, or four VS Code windows, from stampeding the same provider, and a limit that resets when a window closes is not a limit. The installation fact is what stops a second VS Code profile on the same machine from asking you to install something that is already there.

**What is deliberately not in that folder: your API key.** It stays in VS Code's secret storage (`context.secrets`) for the one profile that stored it, and a second profile inherits the installation fact and **nothing else** — not your consent, not your access mode, not your key. Putting a key in a plain file to make it convenient across profiles would undo the rule that keeps it out of every log and report this Toolkit writes.

Deleting the folder is safe and is the whole of the Toolkit's machine-level state: the next check rebuilds it, and you will be asked to confirm consent again in each profile because consent is stored in the profile, not here. Removing the Toolkit's per-profile state is done from the panel with **Reset**, which withdraws your confirmation and says so before it does it.

## Choose a goal, not a server

Assistant clients cap how many tools one session may enable — Copilot agent mode refuses more than **128 enabled tools**, and selection reliability starts dropping well before that, around **30–50 tools**. Tool definitions are re-sent with every request, so a wide tool surface is a recurring context cost, not a one-off cost. The toolkit therefore lets you trade surface for focus, and no preset ships more than **12 toolkit tools**.

| Preset | Goal | Toolkit tools | External tools (estimated) | Total |
|---|---|---|---|---|
| Read and cite a document | One PDF/DOCX/Markdown → cited report | 4 | 0 | 4 |
| Search my own notes | Find passages in your Markdown/text and reopen them | 3 | 0 | 3 |
| Verify a citation | DOI resolution and reference comparison | 2 | 0 | 2 |
| Prepare a Zotero import | Collect references → RIS file you import | 5 | 0 | 5 |
| Read, search, cite and write | Full document + metadata surface, no index (Recommended default) | 10 | 0 | 10 |
| **Full research workflow** | Read → index → retrieve → resolve evidence → record a claim → report (**Full default**) | 11 | 0 | 11 |
| Documents, citations and third-party evidence | Document/citation tools + GitHub read-only + Playwright core | 10 | 36 | 46 |
| Maximum research lab | Widest supported surface under the ceiling | 10 | 91 | 101 |
| Index, search and record claims | Your own corpus → stored claims with evidence links (Full only) | 11 | 0 | 11 |

Basic offers the first two presets, Recommended Research offers the first five, and Full offers all nine. Each package has exactly one default preset; a saved preset that the selected package does not offer falls back to that default and the panel says so. The panel also distinguishes the preset you **saved** from the one currently **applied** to the assistant's tool list. Recently used presets are offered first. The preset reaches the managed workers as `RESEARCH_STACK_TOOL_PRESET`, so only the tools serving that goal are registered and a server the goal does not use is not offered.

**Context estimate.** After component setup, the receipt stores the measured size of every discovered tool definition (name + title + description + input schema; characters ÷ 4, plus 40 tokens of framing per tool). Every figure states its basis: **measured from this worker's tools/list**, **partial** (some tools measured, the rest at the vendor figure), or **vendor estimate at 640 tokens per tool definition**. External counts are published vendor toolset figures, never presented as measurements taken by this extension.

Every shipped tool also publishes a title and read-only/destructive/idempotent annotations, and the workers answer `tools/list` with a 300-second private cache hint, so a client does not re-fetch the same definitions on every turn.

## Read the inventory correctly

**Installed** means the running editor/extension, editor registry, setup receipt or selected Python environment supplied installation evidence. **Ready** means the specific check in the row succeeded (host running, version command, SDK import, library test, real MCP fixture read/report or corpus/record-store round trip). **Files prepared** and **Configuration present** do not establish an installed or running MCP server. **Not verified** identifies a client/kernel/account/service first task still required. **Not detected** means absent from inspected locations, not a machine-wide absence. **Planned / Not bundled** describes toolkit integration status even when unrelated software exists elsewhere.

The readiness text now states setup completeness as well as gates: `Package setup for Full: 3 of 4 component steps installed, 1 recorded but needing repair (files it produced are missing), 1 optional step(s) deliberately not installed · G3 not passed.` That line describes what this workspace has installed and observed; it does not close a gate.

Host-tool rows report where the tool was resolved from and the version its version command reported, or the categories searched when nothing was found. A tool that exists but does not answer `--version`, or that is older than the registry minimum, is reported as detected with a failed check — not as installed, and not used by setup.

The extension shows its actual running version. Python worker and dependency versions come from the inspected environment, not catalog requirements or your selected package. Editor-extension presence does not prove authentication or kernel execution. The running managed worker is verified through real local MCP fixture tests. No external provider or Zotero endpoint is contacted during those checks. The [walkthrough](guides/onboarding.md) shows how to complete each first functional task.

## Preview scope

Selecting a package or a tools preset saves a preference. Neither installs, removes, nor configures components; a preset only changes which tools the toolkit registers when its managed servers start. Setup runs only when you start it. Basic/Research remain prototypes with G1/G2 open; Full is a foundation with G3 open, and its shipped slice is now real: a persistent workspace corpus index and a standard-library SQLite record store (schema 3) with ten verbs — `index_corpus`, `unindex_corpus`, `search_corpus`, `verify_sources`, `evidence_read`, `claims_read`, `claims_write`, `claims_export`, `store_status`, `store_maintenance` — where the everyday workflow verbs are separated from the destructive maintenance verbs. Markdown and text files, and now PDF and DOCX files, can be indexed into that store with their original-document locators. Vector search, embedding models, DuckDB/Qdrant, HTTP index services, external account/service provisioning, notebook kernel setup and automatic updates remain separate. Successful reading checks prove the tested local protocol workflow and do not close every profile gate or establish assistant authorization. 0.3.9 does not install uv itself, does not run setup silently or in the background, does not execute notebook kernels, does not connect to external providers, does not build the extraction-to-index bridge, and does not OCR a scanned page. This version does not complete G4.

The private VSIX contains the controller, install-plan engine, diagnostic script/probe, GUI assets, registry, Markdown guides, reviewed worker source/locks, reviewed overlay templates and the reviewed topic skill bundles with their generated catalog, with no production npm dependencies or prebuilt Python environment. The panel accepts validated component IDs, validated step ids, boolean settings and fixed actions. Every external tool run goes through one reviewed module, `extension/runner.js`: a single `execFile` boundary with `windowsHide: true`, `shell: false`, an 8-second default timeout for probes, an 8 MiB output cap and bounded report text. Host-tool lookup is `extension/hosttools.js`, preflight is `extension/preflight.js`, step bodies are `extension/steps.js`, status wording is `extension/status.js`, log/status persistence is `extension/setuplog.js`, and the uv-free comparison of a shipped lock against its shipped project file is `extension/lockfile.js`. No command is read from MCP configuration. Setup explicitly syncs only the toolkit-owned environments. Reading checks explicitly start temporary local stdio MCP servers; selected-document reads require a file choice inside the workspace. See the [onboarding check disclosure](guides/onboarding.md) and [VS Code webview guide](https://code.visualstudio.com/api/extension-guides/webview).

## Build and verify from source

From `extension/`, run `npm ci`, `npm test`, `npm run package`, then `npm run verify-package` and `npm run check:payload`. Both gates take the artifact path from `extension/vsix-manifest.json`, so they audit the VSIX this release cuts instead of an older one. `python3 scripts/lockintegrity.py` reports whether every lock this toolkit ships matches the project file beside it, and exits non-zero when one does not. The repository also includes real Extension Host tests (`npm run test:host`), a panel renderer check that needs nothing beyond Node (`npm run test:panel` — it runs the shipped panel script in a DOM shim and prints a verdict per assertion, and says plainly what it cannot prove), and a browser renderer test (`node test/browser.test.js`). The latter uses development-only Playwright, resolved from your test environment; set `PLAYWRIGHT_CHROMIUM_EXECUTABLE` when using an existing Chromium executable. No browser is shipped in the VSIX.
