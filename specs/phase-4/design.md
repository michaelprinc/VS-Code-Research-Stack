# Phase 4 packaging and verification design

Revision: 0.3.3-preview. G1–G3 remain open; this design covers GUI preferences, tool presets, packaging, and activation seams.

## Source and extension boundary

`extension/` is an independent CommonJS extension package with exact development-tool versions in `package-lock.json`. A separate `vsix-manifest.json` is staged so npm scripts, dev dependencies and `private` metadata do not leak into the installed manifest. Stable host APIs provide commands, Quick Pick, application-scoped configuration, output, clipboard, a native TreeDataProvider, status bar and a WebviewPanel. Activation at `onStartupFinished` initializes shortcuts; a panel opens only on request or explicit startup opt-in. Commands and sidebar access also activate the extension. No Python worker or component setup runs on activation, and no proposed API or extension pack is used.

## GUI and state flow

The sidebar supplies discoverable shortcuts; the singleton panel supplies package cards and boolean interface options. `extension/ui.js` produces fixed HTML with a random script nonce and a `default-src 'none'` CSP. Only packaged `media/` resources are permitted. External CSS uses VS Code theme variables with visible focus and responsive layout. The renderer renders host state with `textContent` and never treats workspace names as markup. Host messages accept only known package IDs, two boolean option keys, fixed actions, valid workspace indices and registered component IDs; arbitrary command IDs are rejected. Settings failures are shown in a live feedback region and the GUI resynchronizes with stored values. User preference writes are serialized within the extension instance.

The existing `researchStack.selectedPackage` key is preserved for upgrades from 0.2.0. Configuration, workspace-folder and trust events refresh sidebar/status/panel context. Renderer startup sends `ready`, so reopening/reloading a webview receives fresh state. Panel message listeners are disposed with the panel; extension-owned commands/providers/status/output are disposed with the context. Help opens the packaged Markdown guide, and copying readiness uses the host clipboard only when requested.

The real Extension Host test exercises packaged contributions, panel construction/reuse, commands and preference persistence over two launches. A separate Playwright renderer test drives actual radio/buttons/checkboxes against a mock host bridge, verifies keyboard saving, external changes, error messages and screenshot layout in dark/light/high-contrast themes. That test does not constitute native editor visual acceptance on every host. Webview design follows the [official guide](https://code.visualstudio.com/api/extension-guides/webview).

VS Code requires an extension manifest at the root of the package and an `engines.vscode` compatibility range ([manifest reference](https://code.visualstudio.com/api/references/extension-manifest)). This preview declares 1.140.0 as its minimum candidate as retained from the 0.2.0 preview; the 0.3.2 GUI is tested on the now-installed 1.141.0 only. `vsce` is Microsoft's packaging tool and accepts `.vscodeignore` or a package `files` allowlist; this package uses `files` only and invokes the pinned tool ([VS Code packaging guide](https://code.visualstudio.com/api/working-with-extensions/publishing-extension)).

## Integrity chain

1. `npm ci` resolves the checked-in exact lock. `npm audit --omit=dev` validates there are no shipped production dependencies; full `npm audit` covers build/test dependencies.
2. `vsce package --no-dependencies` creates one VSIX without npm runtime dependencies.
3. `scripts/verify_vsix.py` opens the archive, validates path/type and exact member allowlist, reads every CRC-checked member, compares package payload bytes against the source files, verifies the extension identity and absence of network/process primitives outside the reviewed bounded diagnostics runner, computes SHA-256 and enforces package/unpacked size ceilings.
4. `code --install-extension` installs the exact file into a disposable `--user-data-dir` and `--extensions-dir`; the isolated CLI listing confirms the installed identity/version.
5. `@vscode/test-electron` launches the installed reference VS Code executable and loads the extension payload extracted from the VSIX. The Extension Host checks contributed command discovery, Basic/Full/Recommended/Full transitions, persisted preference after a host restart, truthfulness of G1–G3 status, first-command time and warm command p95 over 100 invocations.

The hash proves byte identity for this artifact only. No code signature, trusted catalog, Marketplace publisher, SBOM of the whole repo or runtime lock has been established. VSCE packaging warnings for the absent repository license are not suppressed by claiming a license; the private preview marks itself `UNLICENSED` and explicitly skips the missing-license-file check.

## Scalability interpretation

The preview establishes that a tiny zero-runtime-dependency extension can be installed and invoke a status command with low in-process overhead. It does not establish multi-window transaction safety or scalability of future downloads, databases, embeddings, corpus indexing or provider APIs. The Phase 4 package target of 50 MiB remains a proposed release budget; the audit also records unpacked bytes to catch compressed payload bloat.

## Known gaps

No complete profile installer/resolver, SecretStorage, workspace merge, update journal or data lifecycle is wired into this extension. A bounded worker setup adapter and native MCP definition provider are implemented. The local registry and bounded inventory checks are implemented; live service health remains unverified. It does not accept custom profiles and does not install, remove, or configure components when the selection changes. G1/G2/G3 are prerequisite failures, not silently remapped readiness states. The package does not use a full runtime installer or service/model payload.

## Component observations and scalable guides

`diagnostics.js` creates editor-only state on activation and checks local tools and one selected environment only on explicit request. `probe.py` runs with isolated Python and performs library smoke checks in memory. Installed versions come from the executing host or distribution metadata, never the desired profile/catalog. Source presence, installed distribution, working library and working MCP session remain separate. Remote/restricted checks do no executable or workspace inspection. A generation token drops results after workspace/extension changes. The runner uses fixed argument lists, no shell, bounded per-operation timeouts and a 64 KiB output limit; portable MCP configuration is inspected without invoking server commands or exposing environment values.

`components.json` ties each component to its own `guides/<id>.md`, fixed official URL and review date. `scripts/build_guide_index.py` validates coverage/content and generates the hub during packaging. Offline relative links are preserved by disabling VSCE rewriting. Documentation maintenance edits individual sources and regenerates the index; new registry rows automatically reach the GUI and hub. Online latest-document links complement versioned offline snapshots. Guide and registry bytes are included in the exact archive audit.

## 0.3.2 functional local slice

The GUI setup action previews the selected workspace, isolated `.research-toolkit/managed/worker-0.3.2` path, Python 3.12 and locked package downloads. The VSIX contains reviewed worker source/locks with a hash manifest, not a prebuilt runtime. Only this owned project is synced; unrelated project environments and existing MCP files remain unchanged. Fixed versioned paths, source integrity checks, exclusive workspace setup locks and retryable stages prevent silent source replacement and competing setup. Existing edited managed sources are preserved and block execution.

The stable MCP definition provider supplies managed Basic and Research servers without merging user JSONC. Provider construction uses the positional constructor verified against VS Code 1.141.0 and its published API reference, with `cwd` assigned separately. It returns no servers on restricted/remote workspaces or before a successful setup receipt. Real protocol tests verify synthetic PDF/DOCX extraction, source hashes/locators, report creation, local BM25 retrieval and RIS preparation. Selected-document reading is an explicit GUI file choice under the selected workspace, with a bounded preview and no source mutation. Blank/scanned PDFs remain failed text checks. Runtime/provider tests do not establish assistant authentication or external scholarly/Zotero access. Notebook kernel setup and planned vector/storage/browser integrations remain separate.

## 0.3.3 goal-based tool presets

`extension/presets.json` is the single registry: preset id, label, goal, tips, prerequisites, the toolkit tools it enables, optional third-party estimates, the packages that offer it and the package it defaults for. `src/research_stack/presets.py` mirrors the same ids and tool sets for the workers, and `tests/test_presets.py` plus `extension/test/presets.test.js` fail if the two drift.

Resolution order is `researchStack.toolsPreset` → validity against the current package → package default. The MCP definition provider passes the resolved id in the server environment and omits servers whose tools the preset does not use, so goal shaping happens at tool registration rather than by hiding servers. Server-based filtering was rejected as the primary mechanism: users choose goals, and one goal can span both workers while one server can serve several goals.

Context estimation has two layers. Measured: `extension/functional_check.py` records each discovered tool's name, title, description and input-schema size, estimates `characters ÷ 4 + 40` tokens of framing, and stores the per-server totals in the setup receipt; the control panel reads them through the managed-runtime receipt. Estimated: external servers use published vendor toolset counts (GitHub default toolsets ≈52, read-only subset ≈12, Playwright core ≈24, Zotero community ≈15) at 640 tokens per tool definition, always labelled as estimates because this extension neither starts nor measures those servers. Budget bands are 128 (client ceiling), 96 (warning) and 50 (accuracy band).

## 0.3.4 declarative install plan and record store

`extension/components.json` (schemaVersion 2) is the install contract; `extension/installer.js` is the only engine that interprets it. The registry answers four questions per component — who installs it (`managed`/`host`/`editor`/`external`/`planned`), which step provides it, how the toolkit verifies it, and what the operator should do next — so a new component becomes a registry entry plus a guide rather than a new control-panel feature. `installSteps` declare order, prerequisites, the components each step provides and which package steps are optional; `packages` declare the step list plus the gate and support level the readiness text reports.

`runPlan` resolves the selection against the workspace receipt in `.research-toolkit/managed/worker-0.3.4/installation.json`, runs only missing or outdated steps, writes the receipt after each successful step, and returns what ran and what was skipped. `stepStatus` compares the recorded `toolkitVersion` with the running release, which is what makes **Update outdated components** a distinct action from **Set up package components**. Process execution is delegated to the reviewed bounded `execFile` runner in `diagnostics.js`; the installer itself contains no shell, no network primitive and no command read from MCP configuration. Overlay files are written with the `wx` flag, hash-verified against `worker/bundle.json`'s `overlayFiles`, and preserved when they already exist; a linked path is refused.

The Full slice is `src/research_stack/records.py` plus `src/research_stack/lab_server.py`. The store is one workspace file, `.research-toolkit/store/research.sqlite3`, using only the Python standard library: `meta`, `sources`, `chunks`, `claims` and `claim_evidence`, with chunk identities shared with the in-memory BM25 path in `full.py` so an indexed chunk and a searched chunk are the same record. Bounds are explicit (1000 sources per call, 20000 stored chunks, 2000 claims, 2000-character statements, 200 evidence links). Writes are separated from reads and annotated so a client can gate them; `store_maintenance` requires `confirm=true` for `vacuum` and never overwrites a backup. `init-lab` writes `.research-toolkit/lab-state.json` describing what actually exists; it deliberately does not write a `full-profile.json` claiming a loopback index service the toolkit does not run.

Tool-surface decisions are enforced in code and tests: `presets.py` and `presets.json` are kept in lockstep, `corpus-lab` is the only preset that enables the five corpus verbs, no preset exceeds 12 toolkit tools, and `research-lab-max` keeps 28 tools of headroom. `tool_meta.py` centralises annotations and the `tools/list` cache hint (`ttl_ms` 300000, `scope` private) so all three servers answer identically, and `register_tools` registers in sorted name order so a client's tool list is stable across releases.
