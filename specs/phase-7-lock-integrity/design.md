# Phase 7 design — 0.3.7

## 1. Measured facts this design rests on

All measured on this host with real uv binaries (downloaded from astral-sh releases), against the exact shipped
pair and the exact command `runtime.js` issues.

| Measurement | Result |
|---|---|
| `uv sync --locked --no-dev --python 3.12 --project <worker> --no-config` on the **shipped 0.3.6 pair** (pyproject 0.3.6, lock 0.3.4) | **exit 2** on uv 0.5.0 and **exit 1** on uv 0.13.6, both printing the same sentence: "Resolved 40 packages … The lockfile at `uv.lock` needs to be updated, but `--locked` was provided." Reproduced; not inferred. The number is not stable across the range — 2 on uv 0.5.0–0.7.22, 1 on uv 0.8.5–0.13.6 — which is why detection never uses it. |
| Same command after the lock's root entry records the manifest version | **exit 0** on uv **0.5.0, 0.6.10, 0.7.22, 0.8.5, 0.9.30, 0.10.7, 0.13.6** — the whole supported range down to the registry floor `uv >= 0.5.0`. |
| `uv lock` (uv 0.13.6) on the shipped manifest | Changes **two lines only**: `revision = 3 → 5` and the root `version = "0.3.4" → "0.3.7"`. The lock holds 40 `[[package]]` entries before and after; the root entry's version is the one that changes, and the 39 third-party pins and their hashes are unchanged. The regenerated file is byte-identical to the corrected lock. |
| `uv lock --check` availability | Absent in uv 0.5.0 (exit 2, `unexpected argument`), present from 0.6.10 through 0.13.6. A capability probe is required (R7-12). |
| Lockfile `revision = 5` | Written by uv 0.13.6 (`revision = 3 → 5`). uv 0.5.0 writes **no** `revision` key at all — its own `uv lock` drops the line — but it reads and accepts the revision-5 lock: `uv sync --locked` on the shipped pair exits 0. Raising the revision is therefore not a compatibility risk for the declared uv floor. |
| `uv sync --frozen` on a drifted pair | Proceeds (skips the freshness check) — which is why it is used only as a **logged fallback after** the drift has been named, never as the default. |

## 2. Decisions

| ID | Decision | Why |
|---|---|---|
| **DD7-01** | Fix the pair by regenerating the lock with a pinned uv (0.13.6), not by hand-editing the version line. | The regenerated bytes are what uv itself produces; the diff is two lines and the package set is untouched, so the reviewed supply-chain promise holds. |
| **DD7-02** | Compare pairs with a uv-free reader in **two** languages: `scripts/lockintegrity.py` (build/audit/tests) and `extension/lockfile.js` (the extension's own pre-run check and diagnosis). | The build gate must run without uv; the extension must diagnose without spawning a helper process. Both read only the fields uv compares. |
| **DD7-03** | Gate at three points: bundle build, VSIX audit, test suite. | A single gate can be bypassed by hand-packaging. The audit checks the **packaged** pair so an artifact cut from a stale tree cannot pass. |
| **DD7-04** | Runtime tiers: bundled-pair self-check → `uv sync --locked` → on drift, one `uv sync --frozen` fallback, logged and surfaced. No `uv lock` in the managed directory. | `uv lock` would rewrite a file `bundle.json` hashes and `validateWorker` verifies, trading a reproducible integrity model for a cosmetic label. `--frozen` installs exactly what the shipped lock pins and mutates nothing. Astral's own recommendation for this failure is `--frozen` ([uv #15643](https://github.com/astral-sh/uv/issues/15643)). |
| **DD7-05** | Recognise drift from uv's own sentence, and keep it out of the transient-retry path. | Retrying a manifest/lock disagreement runs the same refusal twice and hides it. |
| **DD7-06** | Scrub inherited `UV_*` variables that change the reviewed command's meaning, then set the five reviewed `UV_*` values plus `UV_PROJECT_ENVIRONMENT`, which is derived from the project directory. | `--no-config` neutralises config files, not the environment; a user's mirror or `UV_LOCKED` can make a byte-correct lock look stale. |
| **DD7-07** | Keep the release identity three-part and assert it is a version vsce can package. | `semver.valid` rejects `0.3.6.1`, so a four-part identity is not a shippable release at all ([vscode-vsce #415](https://github.com/microsoft/vscode-vsce/issues/415)). Relaxing the pattern would have hidden the constraint instead of recording it; the release is 0.3.7 and `tests/test_release_identity.py` now names the packaging rule in its failure message. |
| **DD7-08** | Derive the artifact name from `extension/vsix-manifest.json` in npm scripts. | Verification must point at the artifact the release actually cut. |

## 3. Module changes

| File | Change |
|---|---|
| `scripts/lockintegrity.py` | uv-free pair reader (name, version, `requires-python`, specifiers, groups, revision bound), `check_tree`, `shipped_pairs`, `lock_dependency_set`, CLI with JSON output and exit code. |
| `scripts/build_worker_bundle.py` | Refuses to bundle a stale pair; re-checks the pair it wrote (R7-02). |
| `scripts/verify_vsix.py` | Reads `extension/worker/pyproject.toml` and `extension/worker/uv.lock` **from the archive** and runs the same comparison (R7-03). |
| `tests/test_lock_consistency.py` | New suite: shipped pairs current, worker pair byte-equal to the reviewed source, drift detector proven on a synthetic fixture, revision bound, real `uv lock --check` when uv exists (R7-04, R7-05). |
| `extension/lockfile.js` | New reviewed module: drift signature, lock/pyproject readers, `pairProblems`, `dependencyPins`. No process, no writes. |
| `extension/runtime.js` | Bundled-pair self-check before any uv call; drift-aware setup tiers; three-part `WORKER_FOLDER_PATTERN` (`/^worker-(\d+\.\d+\.\d+)$/`); `functionalCheck` honours the setup timeout. |
| `extension/runner.js` | `setupEnvironment` scrubs conflicting `UV_*` before setting the reviewed values; `describe()` names a lock-drift refusal precisely; wall time across attempts reported. |
| `extension/package.json` | `verify-package` / `check:payload` resolve the artifact from `vsix-manifest.json`. |
| `tests/test_release_identity.py`, `extension/test/unit.test.js` | Version shape stays three-part; both refuse a fourth part (`unit.test.js` asserts `/^\d+\.\d+\.\d+$/`, `test_release_identity.py` asserts `worker-0.3.6.1` is not a runtime). |
| `extension/test/module-boundaries.test.js`, `scripts/verify_vsix.py` inventory | `lockfile.js` joins the reviewed module set. |

## 4. Failure-mode review of the new code

| Scenario | Behaviour |
|---|---|
| Bundled pair disagrees (a future release repeats the 0.3.6 mistake) | Setup stops **before** spawning uv: the message names both bundled files and the disagreeing fields, says this is a packaging defect of this build, and records the attempt. No file is written. |
| Host uv calls a byte-correct lock stale (mirror/index env, uv-version difference) | `--locked` refuses → drift recognised → one `--frozen` attempt installs exactly the pinned set → step reported with the drift named and the fallback recorded in the log, receipt and panel. |
| `--frozen` also fails | The step is `failed` with both attempts' evidence; the plan continues past it and blocks only dependents (Phase 6 behaviour unchanged). |
| Host uv is 0.5.x (no `uv lock --check`) | Nothing depends on that flag at runtime; the capability probe is a development-host gate only. |
| A malformed runtime folder exists (`worker-0.3.6.1`, `worker-0.3`) | Skipped. No release can name such a folder — vsce validates the extension version with `semver.valid`, which takes at most three numbers — so accepting it would only hide a manifest that cannot be built. |
| User has `UV_INDEX_URL` set to a mirror | Removed from the child environment; the reviewed command always resolves against the pinned index recorded in the lock. The removal is named in the failure text (`scrubbedUvVariables`), so a host-specific problem is not reported as a generic one. |
| The bundled pair cannot be parsed by the toolkit's own reader | Refused as a packaging defect with the same wording as a disagreement, `error.lockDrift.source = "bundled"`, no process, no write. A reader crash is never surfaced to the operator. |
| uv refuses the pair **and** the toolkit's reader agrees | Refused with the packaging wording. `--frozen` is not attempted: installing a resolution this uv already called stale would turn a broken build into a warning. |
| uv refuses the pair and the toolkit's reader finds nothing wrong | One `--frozen` attempt, recorded. Measured on the drifted 0.3.6 pair: exit 0 on uv 0.5.0 through 0.13.6. |
| The notebook analysis pair this toolkit just wrote is stale | `steps.js` reads the pair from disk and refuses before running uv. |
| `node extension/scripts/package.js` run directly on a stale tree | Refused before anything is staged (`assertWorkerPairCurrent`), so the lock gate does not depend on the npm script chain. |

## 5. Decisions added during review

| Id | Decision | Reason |
|---|---|---|
| **DD7-09** | Keep `UV_PYTHON_DOWNLOADS: "automatic"` as a reviewed value even though it overrides a host's `never`. | The managed worker needs CPython 3.12 and the host may not have one; a host setting that guarantees failure is not a preference to preserve. Recorded because it is a deliberate behaviour change, not neutralisation. |
| **DD7-10** | Gate the `--frozen` tier on the toolkit's own reader, and measure the tier with real uv. | The tier is only defensible for a disagreement the toolkit cannot reproduce. Where the reader agrees with uv the build is broken and must be refused, not softened. Receipt: `uv sync --frozen` exits 0 on the drifted pair on all seven uv versions. |
| **DD7-11** | Fix the readers' requirement comparison (extras, markers, array parsing, table boundaries) before another dependency is added. | The shipped pair has no extras or markers, so 0.3.7 passes today; the first extra- or marker-bearing dependency would have made a valid build refuse. Found by an independent review, not by a failure. |
| **DD7-12** | The single reviewed process boundary is now **one bounded `childProcess.spawn(` plus one `childProcess.execFile(` tree reaper**, both `shell: false` + `windowsHide: true`, in `extension/runner.js`. The bounded run is a `spawn` because Node's `execFile` builds its own spawn options internally and passes only `cwd, env, gid, shell, signal, uid, windowsHide, windowsVerbatimArguments` — `detached` is dropped (measured on this host, Node v24.22.0: an `execFile` child keeps the toolkit's own pgid, a `spawn` child with `detached: true` becomes its own group and session leader). With `execFile` a `kill(-child.pid)` would aim at the **editor's** process group. The child is therefore started in its own POSIX process group and a stopped run is reaped with `process.kill(-pid, "SIGKILL")`, or on Windows with `taskkill.exe /PID <pid> /T /F` while the direct child is still alive to name its tree; the capture limit moved from `execFile`'s `maxBuffer` option to a manual `MAX_BUFFER_BYTES` counter in the boundary. Still one place where a tool runs — `scripts/verify_vsix.py` and `extension/test/module-boundaries.test.js` now enforce that shape (one `spawn`, one `execFile`, both bounds on both call sites, no `shell: true`), and `tests/test_vsix.py` refuses a runner that reintroduces a second spawn or a shell. Receipt: the reviewer's own probe (`/tmp/win-037/probe6_process_tree.js`) wrote its grandchild marker 1.6 s after the RunError before this change and writes nothing after it. |
