## Open, by design

| Item | Why it is not closed here |
|---|---|
| A live Zotero answering on `localhost:23119` | No Zotero is installed in this container. The container-side substitute is the recorded refusal: `outcome: "not-installed"`, `code: "ZOTERO_NOT_AVAILABLE"`, with the statement that no library file was opened (`probe-receipt.json`). |
| A real Semantic Scholar API key | No key exists here and none may be created by this repository. The container-side substitute is the licence gate: `outcome: "auth-required"`, `code: "PROVIDER_TERMS_NOT_ACKNOWLEDGED"`, no request sent. |
| A live VS Code Extension Host | `npm run test:host` needs `VSCODE_EXECUTABLE_PATH`, which this container does not have. The wiring is proven through the same harness the other host tests use and through the installed payload check. |
| Windows 11 install and paths | Not reachable here. |
| INT-12 — sharing the decision across VS Code profiles of the same OS user | Deliberately not implemented. globalState and SecretStorage are per-profile; a cross-profile store needs a location, a format and a threat model this release has not written. The record is global **to the profile**, which is what INT-03 asks for. |
| INT-13 — guided Zotero installation through the platform package manager | Deliberately not implemented: the Toolkit would have to run an installer it has not reviewed. The guide names the official installer and the readiness check reports what it found. |
| INT-14 — a remote Zotero library | Out of this release. |
| Zotero write access | Out of scope by decision. The probe reads, and the worker's own detail states that nothing was written. |
| Whether the provider's licence permits what the operator intends | The Toolkit records that the operator reviewed the licence and says plainly that the record is not a grant of rights. It cannot judge the intended use. |
