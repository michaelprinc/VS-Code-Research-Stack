# VS Code Research Stack — Phase 1 Basic, Phase 2 Researcher, Phase 3 Research Lab

This repository contains the Windows reference implementation prototype for the Basic / Research Starter package and an additive Phase 2 Researcher prototype. Both use portable workspace content, locked `uv` projects, and local stdio MCP workers. **G1–G4 all remain open: this repository is not yet a supported cross-platform release, and no gate has passed.** The [Phase 1 gate report](evidence/phase-1/gate-report.md) is versioned here, and its own header records `Outcome: **partial prototype; G1 not passed**`; the [Phase 2 report](evidence/phase-2/gate-report.md) records `Outcome: **prototype implemented; G2 not passed**`, the [Phase 3 report](evidence/phase-3/gate-report.md) records `Outcome: **partial foundation implemented; G3 not passed**`, and the [Phase 4 report](evidence/phase-4/gate-report.md) records `Outcome: **0.3.2 local document workflow passed; full G4 remains open.**`

**About this file.** `scripts/build_worker_bundle.py` copies this README byte-for-byte into `extension/worker/README.md`, which is packaged inside `worker-<version>/`. The links below are valid when this file is read in the repository; they do not resolve from inside the packaged worker folder. The Marketplace Details page is [extension/README.md](extension/README.md), packaged separately as `extension/readme.md`.

## Quick start

```text
uv python install 3.12
uv sync --locked --python 3.12
uv run --locked research-stack inspect
uv run --locked research-stack init "<your research workspace path>"
```

Open the created workspace in VS Code, inspect `.mcp.json`, trust the workspace only after reviewing the configuration, and use **MCP: List Servers** to start the `research-stack-basic` server. It can read selected PDF/DOCX documents and write new Markdown/DOCX reports. The document workflow has no external account requirement. Copilot, GitHub remote access and NotebookLM import are optional and not included in this prototype's verified integration.

See [setup and operation](docs/implementation/phase-1-basic/setup-and-operation.md), the [Phase 1 specification](specs/phase-1/spec.md), and the [gate report](evidence/phase-1/gate-report.md).

## Phase 2 Researcher prototype

Add the Phase 2 overlay to a disposable Basic workspace with:

```text
uv run --locked research-stack add-recommended "<workspace path>"
```

The overlay adds a separate MCP server for bounded OpenAlex, Crossref and Semantic Scholar metadata searches; exact-DOI citation lookup; loopback read-only Zotero access; and reviewed RIS preparation. It adds five research skills and recommends the VS Code Python and Jupyter extensions. It does not download papers or run notebook cells automatically. Until 0.3.12 it wrote nothing to Zotero at all; from 0.3.13 the research worker can write to a local Zotero library, but only through `zotero_write`, only with a key you authorized in Zotero's own dialog and the literal confirmation `write-to-zotero`, only after a snapshot of the library has been written into your workspace, and never with a delete or a merge. See the [Phase 2 setup guide](templates/recommended-overlay/research/README.md), the [Phase 2 specification](specs/phase-2/spec.md) with its [acceptance criteria](specs/phase-2/acceptance.md), the phased [implementation plan](docs/implementation/phase-2-recommended/implementation-plan.md) and [checklist](docs/implementation/phase-2-recommended/checklist.md), and the [G2 evidence report](evidence/phase-2/gate-report.md), whose header records `Outcome: **prototype implemented; G2 not passed**`.

To make a user-mediated NotebookLM bundle, run `uv run --locked research-stack export-bundle "<new output folder>" "<selected source 1>" "<selected source 2>"`. Supported copies are PDF, DOCX, TXT and Markdown. This only prepares files and a checksum index; it does not connect to NotebookLM.

For the Full package's local corpus index and record store, run `uv run --locked research-stack init-lab --workspace "<research workspace>"`. It creates `.research-toolkit/store/research.sqlite3` (standard library only) and `.research-toolkit/lab-state.json`, and never modifies your source files. The same step is available in the control panel. `research-stack index-corpus` indexes selected Markdown/text, PDF or DOCX sources (with `--accept-partial` when you choose to accept a partial extraction) and `research-stack verify-sources` re-hashes the indexed sources against the files present now.

### The Full package's corpus index and record store (0.3.4, schema 3 from 0.3.9, schema 4 from 0.3.14)

Full now ships a real slice: a persistent workspace corpus index and a standard-library SQLite research record store (schema 4 since 0.3.14, schema 3 from 0.3.9) under `.research-toolkit/store/`, served by a third managed MCP server with eleven verbs (`index_corpus`, `embed_corpus`, `unindex_corpus`, `search_corpus`, `verify_sources`, `evidence_read`, `claims_read`, `claims_write`, `claims_export`, `store_status`, `store_maintenance`). `index_corpus` now indexes explicitly selected PDF and DOCX sources beside Markdown/text — a PDF chunk carries its page number and offsets inside that page's extracted text, a DOCX chunk its ordered paragraph or table-row item, and no chunk crosses a page or an item — while the Markdown/text chunker `paragraph-window-v1` and its existing chunk ids are unchanged. `verify_sources` is the only verb that may call a source `verified`; the states are `verified`, `changed`, `missing`, `inaccessible` and `unchecked`. A store written by 0.3.8 refuses reads with `STORE_SCHEMA_UPGRADE_REQUIRED` until the **Corpus index and record store** component step runs; that step migrates it forward with additive changes only — to schema 3 in 0.3.9, where migrated rows are labelled `legacy` / `unchecked` rather than back-filled — and to schema 4 in 0.3.14, where the migration adds the `chunk_vectors` table and no vector is invented for a chunk it did not compute. ### 0.3.14 — retrieval, the max presets and bundle archives (17 November 2026)

**Retrieval.** `search_corpus` answers in three modes: `lexical` (the stored BM25 path, unchanged in ranking and in the shape of a hit), `vector`, and `hybrid`. Vectors are produced by the Toolkit's own CPU backend — `rsk-hashing-v1`, 256 dimensions, word tokens plus character 3- and 4-grams combined by signed feature hashing — from the chunk text the store already holds: standard library only, no model download, no network call, no new dependency, no third-party database. It is a **lexical signature, not a semantic model**: it reaches `iluminacích` from `iluminace` and `sandals` from `sandal`, and it does not know that "pilgrimage" and "journey" are the same idea, does not handle negation, and is not cross-lingual. A stored vector is used only when its backend id, its dimensions and the hash of the chunk text it was made from all match what this backend would compute today; a row that fails is counted as stale, never scored, and the refusal names `embed_corpus` as the verb that rebuilds it. `hybrid` fuses the two rankings by a rule the receipt publishes — `0.5 × reciprocal-rank-fusion (k = 60, normalised so a chunk first in both rankers scores 1.0) + 0.25 × best-normalised BM25 + 0.25 × best-normalised cosine` — and each hit carries `lexicalRank`, `lexicalScore`, `vectorRank`, `vectorScore`, `fusedScore` and `backend`, so a reader sees which ranker placed the passage. No cosine threshold is applied anywhere: the modes rank, they do not decide relevance, and a vector score is retrieval provenance, never a claim that a passage supports a statement. `lab-state.json` is rewritten from the store by every store-writing verb and reports the retrieval state as `not-built`, `partial`, `stale` or `ready`. `draft` is now a claim status. The Phase 3 route these gates ask for — a downloaded embedding model, Qdrant, DuckDB, a Research-RAG MCP, a benchmarked relevance study — is still unimplemented and its components are still `kind: "planned"`.

**Presets and Copilot tool selection.** `extension/presets.json` declares **12** preset ids — ten offered and two retired — with a per-preset toolkit ceiling of **20** (0.3.13: 12), a 128-tool client ceiling and a minimum headroom of 20, and the workers register **21** verbs. The three new max presets name the exact tools they select: `research-max-github-full` (16 toolkit verbs + 92 named GitHub tools = 108, 20 tools of headroom), `research-max-github-limited` (20 + 42 read-only named GitHub tools = 62, 66 tools of headroom, with the server's own read-only switch and an explicit exclusion of all 35 write tools) and `research-max-no-github` (20 toolkit verbs, no third-party surface, 108 tools of headroom). Each preset states the verbs it leaves out. `research-lab` and `research-lab-max` are retired — their ids still resolve for anyone who saved them, no package offers them any more, and each names its successor. **Research Toolkit: Configure Preset Tools for Copilot** writes the selected preset's exact GitHub selection into the workspace file the Copilot harness reads for `mcpServers` (workspace-root `.mcp.json`, per-server `tools` array), keeps a copy of what it replaced, refuses to overwrite an entry the Toolkit did not write, refuses the deprecated `.vscode/mcp.json` `servers` shape because that shape has no tool-subset field, and writes no credential — the token appears only as `${GITHUB_PERSONAL_ACCESS_TOKEN}`. The GitHub counts are vendor catalog name counts, not measurements: no GitHub MCP server was started on the build host, so a `tools/list` on a real host is still owed, and a read-only switch is a filter on what a server offers, not a limit on what a token may do.

**Bundle force update, archive and restore.** A normal bundle install or repair still never overwrites a file you edited. **Force Update Topic Skill Bundle (Archive First)** plans with `force: true`, lists every file it would replace and the state it measured for each, and copies the bytes it replaces — before writing anything, never moving them — into `.research-toolkit/bundles/archive/<bundleId>/<archiveId>/` (`archiveId` is a UTC stamp plus a sequence, `20261117T205542Z-0001`), each keeping its workspace-relative path beside an `archive.json` manifest with the sha256 of the archived copy. `archive/index.json` lists every archive and `archive/archive.log` carries one line per archive naming its **absolute** path; a damaged index is rebuilt from the tree and says so. An archive is never rewritten and never deleted, and no retention policy is claimed. **Show Bundle Archive History** lists archives newest first; **Restore Bundle Archive Version** hash-verifies the archived bytes into staging, archives what it replaces and only then writes the older version back.

**Two integration settings.** `researchStack.integrationTimeoutMs` (default **80 000 ms**, allowed **40 000–300 000**) and `researchStack.integrationCooldownSeconds` (default **10 s**, allowed **5–300 s**) replace values that lived as literals in `extension/integrationprobe.js`. `probeBounds()` reads both in one place, clamps an out-of-range value to the stated range and says the clamp — what was set and what actually ran. The bounds are arithmetic on the worker's own limits (34 s Zotero-only worst case, 35 s hosted ceiling), they cover the whole worker call rather than one request, and they cannot raise the worker's per-request timeouts or apply to component setup. The **4 new commands** take `contributes.commands` from 39 to **43**, and each of them has a control in the corpus-and-bundle row of the control panel (`extension/ui.js`) as well as a Command Palette entry: **Force-update topic bundle where a file differs**, **Show bundle archive history**, **Restore an archived bundle version** and **Select the GitHub tools this preset offers Copilot**. Panel behaviour for these commands is proven through `extension/test/harness.js` and the panel check, not through a live VS Code run. The 0.3.14 VSIX **was** built, packaged and audited on the host that cut this release (`npm run verify-package` and `npm run check:payload` both `result: passed`); what has not been done is running it in a real Extension Host on another machine.
